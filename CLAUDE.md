# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Install: `npm install` (native module `better-sqlite3` will compile on install)
- Run: `npm start` (plain `node main.js`)
- Run with auto-restart on file change: `npm run dev` (`node --watch main.js`)
- No build step — plain ESM, run directly by Node (`"type": "module"`, Node >=18)
- No linter/formatter is configured
- Regenerate the guide's world map: `npm run docs:map` (after anything in `data/locations.js` moves — see `data/worldMap.js` below; the suite fails if you forget)
- Test suite: `npm test` (unit + integration), `npm run test:unit` (fast, no `tmux` required), `npm run test:integration` (drives the real game via `tmux` — needs `tmux` installed; the directory-form `node --test <dir>` is broken on this project's Node build, so `package.json` uses shell globs — `node --test test/unit/*.test.js test/integration/*.test.js` — which means a new test file is picked up with no `package.json` edit). Integration tests launch `node main.js` inside a detached `tmux` session and drive it with real keystrokes (`test/helpers/tmux.js`, `test/helpers/bootstrapCharacter.js`); several exercise real timed travel and take tens of real seconds to run (see `data/locations.js`'s `time` fields below) — the full suite takes roughly a minute.
- Test isolation gotcha: `db_backbone.js`, `logger.js`, and `state/autosave.js` each open/resolve their file at **import time** from an env var (`DB_PATH`, `LOG_PATH`, `AUTOSAVE_PATH`), and ES module imports fully evaluate before a test file's own top-level code runs. Any unit test needing isolation must set these env vars *before* any static import of a module that transitively imports one of those three, using dynamic `await import()` inside the test body instead of static imports at the top of the file (see `test/unit/persistence.test.js` for the pattern).

Running the game takes over the terminal via neo-blessed's alt-screen buffer. It also starts a plain `node:http` server (`server_backbone.js`, no Express) on `localhost:4000` — configurable via `server_config` in `config.js` — serving `public/index.html`, a read-only "playercard" web page that polls `GET /api/playercard` every 5s for a JSON snapshot of live game state, rendered across five client-side tabs (Playercard, Toolbelt, Backpack, Quests, Achievements — all populated from the same poll, tab-switching is a pure CSS toggle with no extra fetches). Two export buttons (shown only when `server_config.export` is true, which the payload reports as `exportEnabled`) share one `exportFilename(name, ext)`/`downloadBlob()` pair. **[Export HTML]** downloads `apocylta_pc_<player>.html`: the page cloned whole, with the payload injected as a `<script type="application/json" id="pc-snapshot">`. The script's bootstrap prefers that tag over fetching, so the copy renders itself once, keeps every tab and sub-tab working, and never polls — the live page has no such tag and behaves as before. Three traps that copy walked into and now guards against: the snapshot tag must be the **first child of `<body>`** (the page's own script runs during parsing, so a tag after it doesn't exist yet when the bootstrap looks), `</` in the JSON is escaped (an unescaped closing script tag truncates the file), and neither export button may carry class `tab-btn` (`showTab` queries that class document-wide and would blank every panel). **[Export JSON]** downloads `apocylta_pc_<player>.json` — the same payload, pretty-printed, without the page around it (~19KB against the HTML copy's ~54KB), for pasting into the reader described below. The snapshot bootstrap hides *both* buttons: a static copy can't re-export either way.

**`public/apocylta_player.html` is the reader for that JSON**, served for free by `serveStatic` (which serves anything under `public/` — `index.html` is only special as the `/` default, so the reader needed no route, MIME or server change). It opens on a textarea plus a file picker, and `importPayload()` walks JSON-parse → shape check (`name` string, `skills` array) → `render()`, each in its own catch with its own message, revealing the card **only** once `render()` returned — a throw part-way leaves a half-drawn card, which is worse than the paste box. It has no `fetch` and no `setInterval` at all, which is what lets it sit on a static host with no game near it.

**The two pages share three regions verbatim, delimited by sentinel comments** (`shared:style`, `shared:card`, `shared:render`), and `test/unit/playerPage.test.js` asserts the extracted spans are byte-identical plus that each marker appears exactly once. External shared assets were the alternative and were rejected: `buildSnapshotHtml` clones the live DOM, so a `<link>`/`<script src>` would make the HTML export open unstyled and dead, and the reader would become three files to host rather than one. Three consequences to respect when editing either page: **page-local CSS, markup and bootstraps must live outside the markers** (only the reader has an import panel; only the live page has export buttons and a poll); the shared `render()` therefore **looks its export buttons up in a loop and skips missing ones** rather than assuming them; and `margin-left: auto` had to move off `.export-btn` onto `.header .sub`'s `margin-right`, since the class now matches several buttons that each claimed half the free space (which parked the two header buttons at opposite ends, and shoved the reader's Import button across its own row). `public/apocylta_player.html` was generated by extracting those regions programmatically rather than copy-pasted; regenerate it the same way if a shared region changes substantially. The Playercard tab's combat panel and lifetime kill list hide themselves when `payload.combat` is `null` / `payload.kills` is empty, mirroring how the action line collapses to "Idle". The Backpack tab groups the inventory into type sub-tabs, with a second row for subtypes, shown only once there are 3+ categories to navigate; those use `.subtab-btn`/`.subtabs` rather than the top bar's `.tab-btn`, because `showTab()` queries `.tab-btn` **document-wide** and reusing the class would blank every panel on a sub-tab click. The selection lives in module-level state because the page re-renders from scratch every 5s.

Environment-variable overrides (all optional, mainly used for test isolation — see the gotcha above): `DB_PATH` (SQLite save file, `db_backbone.js`), `LOG_PATH` (log file, `logger.js`), `AUTOSAVE_PATH` (autosave JSON file, `state/autosave.js`), `DEBUG_LEVEL` (overrides `game_config.debugLevel`, `logger.js`), `ALLOW_ADMIN` (overrides `game_config.allow_admin` **in both directions** — see the Admin section).

## Architecture

This is a single-process terminal RPG with three cooperating layers: static data catalogs, a state/engine layer, and a hand-rolled screen-router UI layer over neo-blessed.

### Data/"backbone" catalogs

Top-level `*_backbone.js` files plus `data/*.js` are pure-data modules (plain objects/arrays, small pure/behavior helpers, no classes):

- `item_backbone.js` — the largest file (~2100 lines): `ITEMS`, `MYTHIC_ITEMS`, `UNIQUE_ITEMS`, `STARTER_PACKS`, `METALURGY`, `SMITHING_RECIPES`/`CRAFTING_RECIPES`/`COOKING_RECIPES`/`POTION_RECIPES`, `TREASURE_ITEMS`, `STATIONS`, `TOOLBELTS` (belt items — `{ slingAmmo, potions, backpack, toolbelt }` capacity tiers, where `toolbelt` is the belt's own weight budget and `backpack` is the floor it puts under the pack's), `BACKPACKS` (a second storage ladder, 100→2000 slots, worn in its own `backpack` armor slot — `equipSlotOf` routes them off the `global: { type: "armor", slot: "backpack" }` block with no special case. `data/toolbelt.js`'s `backpackSlotCap` takes the **larger** of the belt's number and the backpack's `capacity`, never the sum: both answer "how much can you carry", so summing would make a leather belt worth +100 slots on top of God's Back and make taking a belt off a real trade. They're **exempt from `RARITY_BANDS`** for the enhancements' reason — the 100-to-1,000,000 ladder is the gate, and no band reaches past godlike's 6000. The slot needed a real `ALTER TABLE` in `db_backbone.js`, unlike the other paperdoll slots which predate any live save), **Every entry also carries a literal `weight` and, for the ~110 that ride the belt, `storeIn: "toolbelt"`** — `weightOf()`/`storeInOf()` beside `equipSlotOf()` are the only readers, and `storeInOf` defaults to the backpack so the field is absent on the other 887. Weight is what both carrying budgets are spent in (`data/toolbelt.js`); `test/unit/itemBackboneConsistency.test.js` pins that every item has a positive one to 2dp, since a weightless item would be free to carry infinitely. Note **`scrap` joined the `RARITY_BANDS` exemptions**: it runs its own 5/25/50 ladder across common/uncommon/rare, and the rare band starting at 100 would price one scrap metal plate above an iron sword — the rarity there grades how often you find it, not what it's worth. **`CONSUME` resolves in three tiers** — `type` → `subtype` → `item`, most specific last, merged by `consumeRewardFor(itemId)` so each tier overrides **only the keys it sets**: `phoenix_kit` changes the xp and output without restating `skill`, and `aegis_kit`'s `output: null` *cancels* the output it would otherwise inherit (absent key = inherit, present key = override, which is the whole mechanism). The subtype tier is what keeps the 26 brewed teas to one entry — but it is keyed by the **bare subtype**, and subtypes are not unique across types (`heal` is both `potion/heal` and `aid/heal`), so an entry added there can reach further than intended. Byproducts are the `crafting`-typed "Empty Items" family (`CONTAINER_TYPES`), and `test/unit/itemBackboneConsistency.test.js` pins that every named output resolves — `empty_bag` was referenced before the item existed, and an unknown id would have been deposited into the inventory as a phantom, since it weighs 0 and `addItem`'s divide-by-zero guard lets a weightless item through. **Potion recipes take an `empty_bottle`**, so the bottle you get back on drinking is a deposit rather than value from nothing. `SHOP_RARITY_DISPLAY` (rarity → level + color; the level drives the barter gate, barter/craft xp and loot weighting — **not** the price any more), `RARITY_BANDS` (the price band each rarity's items must land in, centred on that rarity's old flat price so nothing was re-pitched), `PROPERTY` (the house deed — priced like a station, and like `STATIONS` deliberately **not** in `ALL_ITEMS`, since neither ever enters the inventory; it used to be a bare `const HOUSE_PRICE = 1000` in `ui/screens/shopHousing.js`, the one priced good defined outside this file), and `ALL_ITEMS` (merge of every catalog above, via a `withGlobalDefaults()` helper that applies each collection's own `global: {}` tag block). Also the **fishing section** at the bottom: `FISH` (species → `water`/`caught`/`difficulty`), `FISHING_ITEMS`, `FISHING_RECIPES` and the `FISHING_TYPES`/`FISHING_SUBTYPES` vocabularies. `FISHING_ITEMS` is authored in *fishing* vocabulary — its `type` is `rod`/`bait`/`net`/`hook`/`fish`/`crustacean`/`shellfish`/`mollusk`, none of which `ITEM_TYPES` knows — so `withFishingDefaults()` translates it into canonical items once and exports the result as **`FISHING_CATALOG`**, which is what `ALL_ITEMS` carries. Rods become `tool`/`"fishing rod"`; bait/nets/hooks become `crafting`/`"fishing"` deliberately **not** `tool`, since `equipSlotOf` would otherwise make them fight the rod for the single tool slot when what gates a catch is merely carrying them; catches become `food` with a per-preparation subtype (`raw_fish`, `cooked_food`, `grilled`, `fried`, `baked`, `smoked`, `pickled`) and a `health_boost` of base-per-preparation plus a rarity bonus; and the ancients' body parts (`leviathan_scale`, `tarvus_bone`…), which have no preparation prefix, become `crafting` materials. **`value` is synthesized here too** — the 258 entries are a mechanical cross product (29 species × 6 preparations, plus 4 gear kinds × 6 tiers), so they're the one block with no literal price: `FISH_VALUE_ANCHOR` × `FISH_PREP_VALUE`/`FISHING_GEAR_VALUE`, band-clamped by `bandedFishValue`. Every prep multiplier is **≤ 2.5 by construction** and that is load-bearing — raw fish are `food` and so sellable, so a `health_boost`-proportional price (cooked/raw = 3.0) would make cook-and-sell a money printer across all 174 `FISHING_RECIPES`. **Bait is the one item exempt from `RARITY_BANDS`**: it's spent per catch attempt even on a miss, so a band built for durable gear would price one forged bait at 100 against a rare fish that sells for 60. Every entry keeps its authored vocabulary as `fishingType`/`fishingTier` — that's what `data/fishing.js` gates on. `catchItemsFor(species)` resolves what a species yields: its `raw_<species>` item, or — for the ancients and their kings, which have no raw form — the parts named after it (matched longest-species-first so `leviathan_king_scale` doesn't fall to `leviathan`). **`ALL_ITEMS` is declared at the very bottom of the file**, after the fishing section, because a `const` can't be spread before it's initialized.
- `player_backbone.js` — `RACES`, `CLASSES`, `DIFFICULTY_LEVELS`, `STARTER_ITEMS` (granted to every character regardless of race/class/starter pack — e.g. the starter belt). Difficulty-derived reads live here as small helpers rather than each consumer indexing the table: `profSkillsFor` (creation-wizard skill picks), `gatherTimeFor` (`logic.gatherTime` — **seconds between gather attempts**, 1 on casual to 60 on demon_lord, floored at 1 since it's a modulo divisor against a per-second tick), `encounterTicFor` (`logic.actionTic` — seconds between ambush rolls) and `groupSpawnFor` (`modifiers.groupSpawn` — how much likelier a spawn is to be a pack).
- `skill_backbone.js` — `SKILLS` (**17** trainable skills, not the 18 the source looks like: `cooking` is declared twice and the second silently overwrites the first, so one intended skill is missing. Left as-is deliberately — `state/persistence.js` derives `SKILL_COLUMNS` from these keys, so adding the lost skill means a schema migration), `skillLevelCost(targetLevel) = round(50 * level^1.4)` (a **total-xp threshold**, not a per-level increment), `PROFICIENCY_XP_MULTIPLIER`, `SKILL_BLOCKS` (skill-gated item tiers), and the **player-levelling** block: `playerLevelCost(level) = round(7.2 * level^2.6)`, its exact inverse `playerLevelFromXp`, `playerXpFromSkillLevels`, `playerXpScale`, `MAX_SKILL_LEVEL = 500` and a **derived** `MAX_PLAYER_LEVEL` (572). The player deliberately does **not** share the skill curve any more: it used to, while being fed a tenth of every new skill level's threshold by all 17 skills, which made the level outrun the skills feeding it by an order of magnitude (17 skills at 75 → player level **1295**). `L^2.6` against a skill's `L^1.4` is the whole mechanism — it makes the level trail the skills and read like an average of them without being computed from any: 17 skills at 75 → ~100, and so does driving four or five past 100. `MAX_PLAYER_LEVEL` is computed at module load by summing what every skill taken to `MAX_SKILL_LEVEL` is worth, so it re-derives itself if the curve, the share, the skill count or the skill cap ever move — never hardcode it. `playerLevelFromXp` corrects its algebraic result against the real (rounded) cost function, because it and `grantPlayerXp`'s loop must agree on what an xp total is worth or every load would nudge the level by one.
- `quest_backbone.js` — `QUESTS`, playable via `data/quests.js` + the Quest Board/Journal screens (see below). Each quest has `level`/`locked` gating, a `reward` (`gold`, `xp`), and an `objectives` map keyed by a human-readable label. An objective may carry **`subObjectives`** (a nested map of the same shape — the parent completes when its required children do, and reports `done/required` as its own progress) and **`optional: true`** (tracked and rendered like any other, but never gates its parent or `isQuestComplete`). `defeatEnemy` accepts two shapes — `{ type, quantity }` (count kills of an enemy type) and a bare id array (each named enemy required) — both computed live off `state.enemiesDefeated`, so like `acquireItem` they count progress made before the quest was accepted. `acquireItem` takes three: a bare id, an `{id: qty}` map (**every** entry required — it used to read only the first), and a `{ rarity, type?, quantity? }` descriptor for "any item of this rarity", where `type` is what stops a mythic fish from finishing "Acquire a Mythic Weapon". `learnSpell` takes a spell-id array or the same `{ rarity, quantity? }` descriptor, reading the `rarity` every spell now carries in `magic_backbone.js`. The id `"money"` (and its legacy spelling `"gold"`) in an `acquireItem` means the purse, not an inventory slot — there is no such item, and `STARTER_PACKS` already treats it that way. Both are in `gameState.js`'s `MONEY_IDS` and both mean **base units**; `"money"` is the spelling to use in new data, since `{ gold: N }` now reads like N gold coins when it has always meant N base units.
- `achievements_backbone.js` — `ACHIEVEMENTS` (24 entries: name/description/reward/`req`), evaluated by `data/achievements.js`. The header comment is the **spec for the whole `req` vocabulary**, and the evaluator implements all 13 types, so a new achievement is pure data. Note `reward.xp` is polymorphic here (`number | { player, skill: {…} }`) where quest reward xp is always a plain number. `slayerrr` needs 5 kills in one encounter, which the larger `GROUP_ENEMIES` packs (6–15 members, in `mountain_peak` and the far regions) now satisfy.
- `magic_backbone.js` — `SPELLS`, consumed by `data/magic.js` + the Spellbook screen. The **aid** spells (the eight Blessed/Blessing entries) carry a `duration` in **game minutes** — 600 for the five rare, 1800 for the three godlike — and the clock runs one game minute per real second, so those are 10 and 30 real minutes. `aidSkillBonuses(spell)` resolves an aid spell's `buff` into `{ skillId: bonus }`: it exists because the block is authored in *spell* vocabulary, and one of its keys (`gathering`) is not a skill at all — it fans out to foraging/woodcutting/trapping/fishing via `AID_SKILL_ALIASES`, deliberately **not** mining, since Blessed Pickaxe covers that and the godlike blessings list `mining` and `gathering` as separate entries. It returns `{}` for anything whose `type` isn't `"aid"`, which matters because combat buffs reuse the same `buff` field for a different thing entirely (Haste's `{ speed: 5 }` is a combat stat, not a skill level) and `state.aidBuffs` is rebuilt from stored spell ids on load.
- `currency_backbone.js` — the money system. **Four metals** (`copper`/`silver`/`gold`/`syllic`) × three denominations (`coin`/`ingot`/`slab`), built as the cross product of `CURRENCY_CONVERSION_RATES` and `SUBTYPE_MULTIPLIERS` rather than hand-listed, so `CURRENCIES` can't drift from the rates (it used to, carrying a `"Silver_slab"` whose capital S made the lowercase id undefined). **The copper coin is the base unit and every number in the codebase is an integer count of them** — there is no float money anywhere, and dividing into denominations is a display concern, never an arithmetic one. Bronze was dropped when copper took the base; the metal ratios are unchanged (silver 10× copper, gold 2× silver, syllic 5× gold), so only the unit moved.

  **Ingots and slabs are bulk packaging, not tiers** — an ingot is exactly 10 coins of its metal and a slab 100. That is why the purse has four slots and not twelve, and why values legitimately collide: a `copper_slab`, a `silver_ingot` and a `syllic_coin` are all 100 base units because they are all worth the same. Anything decomposing an amount for display therefore has to pick a canonical ladder, and that ladder is **coins** (`BASE_LADDER`), so an amount always formats exactly one way.

  Prices resolve through **`toBase(value, curType, curSubtype)`**, both defaulting to copper coins, so a bare `value` is a count of copper. `{ value: 3, curType: "gold" }` would be 60 — but **no catalog entry uses `curType`/`curSubtype`, deliberately**: the whole catalog is authored in bare copper so any two prices can be compared by eye in the source, and `formatBase` does the denominating at the shop counter. The purse helpers are `purseTotal`, `addToPurse` (earnings, paid in one named metal), `spendFrom` (returns the new purse or `null` if short) and `purseFromBase` (a whole purse from one number). `formatBase` renders an amount's canonical breakdown; `formatCurrency` renders what a purse actually *holds*, which is not the same thing — see the independent-holdings note under `gameState.js`.
- `enemy_backbone.js` — `BASIC_ENEMIES`/`GROUP_ENEMIES`/`NAMED_ENEMIES`, plus `ALL_ENEMIES` (flat merge, mirroring `ALL_ITEMS`), `getEnemy()`, `isGroup()` and `expandEnemy()`. Consumed by `data/combat.js`, `data/quests.js`, `state/persistence.js` and `server_backbone.js`.

  **A `GROUP_ENEMIES` entry is not an enemy — it's a header** saying a pack spawned and naming who's in it. It declares only `members`, `name` (shown above the current enemy on the combat screen) and `xp` (a completion bonus, ~30% of the members' combined xp, paid on clearing the pack). It has no hp/dps/type/subtype of its own, is never queued as a combatant, and is **never recorded as a kill** — only members reach `state.enemiesDefeated`. `members` is either a list or a `{ id: count }` map; `expandEnemy()` handles both and returns `[]` (not `[id]`) for a group with no usable members, because queueing a group as a fighter would give it `Math.max(1, NaN)` hp — an enemy that can never die.

  One catalog quirk `test/unit/enemyBackboneConsistency.test.js` pins: 16 mage-subtype enemies carry **no `dps`**, only `spells`, and the engine derives their damage from their best attack spell. The same file also guards the invariant that every spawn-pool entry builds a non-empty encounter with finite hp, and that no pack contains `orc_chieftain` — a `subtype: "boss"` entry in `BASIC_ENEMIES` that would otherwise hand out `boss_down` for a routine fight.
- `data/locations.js` — `LOCATIONS`, each with `exits` (`{ label, to, category, time? }` — `category` is `"shop"`, `"path"`, `"airboat"`, `"cave"`, `"in_cave"` or `"teleport"` — it selects the traveling screen's animation, and `ui/screens/traveling.js` treats anything unrecognised as a road, so a new category renders rather than crashing; an exit with a `time` value, in seconds, becomes a real timed trip via `data/travel.js`, one without it stays instant), an optional `mine` field naming a `MINE_LOCK` tier (read by `getMineType()`, consumed by `data/mining.js` — a location with the `mine` hub feature but no `mine` field lists nothing), an optional `water` field (`"freshwater"`/`"saltwater"`, read by `getWaterType()`, consumed by `data/fishing.js` — the fishing analogue of `mine`, and a location offering the `fish` action without one has nothing to catch), and a `flavorText` that is **either a plain string or an array** whose entries may be `(state, location) => string | null` functions (see `data/flavor.js`). `resolveFlavorText(location, state)` at the bottom of the file turns either shape into the lines to render: a `null` result **drops its line**, and consecutive blanks **collapse**, so a conditional line that stays quiet doesn't leave a double gap. Functions are called unguarded, like `verbFlavor`/`requires` — and since the location screen now re-renders every tick, a throwing one fails immediately rather than lurking. **A line may style any span of itself** with `markup.js`'s `bold`/`underline`/`styled` inside a template string (`` `A sign reads ${bold("NO REFUNDS")}.` ``); a styled line is still just a string, so `resolveFlavorText` needed no change and neither did its "resolves to plain strings" test. `ui/screens/location.js` bolds the `description` head line and wraps every line through `wrapIndented`. Most locations are still one string; only a handful are converted, `interactiveActions`, `hubFeatures`, optional `openHours`, and — on locations with `safe: false` — an `enemies` spawn pool plus an optional `boss` id list, both read by `data/combat.js`. The two black-market interiors are `safe: false` but deliberately have no pool (and no actions at all), which `test/unit/enemyBackboneConsistency.test.js` pins as a known exception. Not every `exit.to` in this file resolves to a defined location yet (`vetron_station`/`kooz_station` both point at undefined ids) — `ui/screens/travel.js`'s digit handler guards against this defensively rather than crashing on arrival.
- `data/actions.js` — `ACTIONS`, in three flavours distinguished by flags that `ui/screens/location.js`'s `startAction()` branches on: timed gathering actions like `gather_scraps`/`chop` (the default), `select: "<screen>"` actions (`fish`) that route to a picker screen which begins the action itself once something is chosen, `instant: true` actions like `rest` that mutate state immediately, and `combat: true` actions (`fight`, plus `challenge_boss` which is additionally gated on `SKILL_BLOCKS.fighting.boss.all.level`) that hand off to `data/combat.js`. Also `beginAction(state, actionId, extra)` (shared constructor snapshotting the acting skill's level/xp for later "gained this session" deltas, plus whatever a selector screen chose — `lootSubtype`/`lootIds`/`species` and `targetLevel`), and `rollLootByType()`, a rarity-weighted loot roller over `ALL_ITEMS`. **A gather attempt can now miss**: `gatherSuccessChance(state, action, targetLevel)` starts from the action's own `successChance` and moves it by `(skillLevel - targetLevel) * 0.02`, clamped to 15–95%, with `rollGatherAttempt()` as the injectable-rng roll. Every attempt used to succeed — `rollLootByType` only returns null on an empty pool — which together with the old flat 3-second cadence is why progression ran away. `targetLevel` is passed in by the selector screens (the ore's / the species' required level), so a mithril seam misses more than tin at the same mining level, and plain gathers default to 1. Each timed action also carries an `attemptVerb` and a `missLine` for the attempt log.
- `data/achievements.js` — the achievements evaluator, mirroring `data/quests.js`: `requirementStatus()` (the analogue of `objectiveStatus()`), `isUnlocked`/`isEarned`, `achievementRows()` (feeds both the screen and the web payload), `grantAchievementReward()` and `evaluateAchievements(state, ctx)`. There is **no accept/claim step** — achievements unlock and pay out the instant their requirement holds, and multiple `req` keys on one achievement are ANDed. Called every tick from `state/gameLoop.js` for the live-derivable requirements, plus once with a `{ combatEnd }` context from `data/combat.js` the moment a fight is *won* (a flee or a death doesn't qualify, and hooking at `endCombat()` instead would read post-revival hp because `resolveDefeat()` restores it first). Two deliberate divergences from the quest equivalents, both commented in place: `reachLocation` means "have reached" (reads `state.locationsVisited`) rather than quests' "standing there right now", and the `combatEnd` `*Max` fields are **upper bounds**, not floors.
- `data/combat.js` — the turn-based combat engine. `spawnEncounter`/`buildEncounter` (an encounter is a **queue** of enemies fought one at a time; a group expands into its members, and `combat.sourceId` keeps the group id so the screen can name the pack and victory can pay its xp bonus; `spawnEncounter` picks from the location's pool **weighted by `groupSpawnFor(difficulty)`** — groups and lone enemies share one list, so a uniform pick made a whole pack exactly as likely as one goblin at every difficulty, and a `groupSpawn` of 0 keeps packs out entirely), `beginCombat`/`endCombat`, `resolveRound(state, action, rng)` (one keypress = one full exchange: player action, then the enemy's), `resolveDefeat`, `attemptFlee`, `usePotion`, plus the exported stat helpers (`playerAttackPower`/`playerDefensePower`/`damageReduction`/`critChance`/`dodgeChance`/`blockChance`/`enemyStrike`). **Every rolling function takes an `rng` last parameter defaulting to `Math.random`** so tests inject determinism rather than stubbing globals — `rollLootByType` in `data/actions.js` gained the same parameter for this. Armor mitigation is a percentage with diminishing returns (`total/(total+K)`, capped at 80%), *not* flat subtraction — equipped `defense` sums past 300 and would otherwise zero out every hit. **Strength trains here too**: `killEnemy()` pays a lump when the dead enemy's `subtype` is `"boss"` — the catalog's own definition, deliberately the same one the combat-end achievement hook uses and **not** `combat.boss`, which merely records that the player chose the boss action and would pay out for picking a boss fight then fleeing — and `awardGroupBonus()` pays a share of the pack's xp for clearing it. A routine kill pays nothing; that's what fighting xp is for. **Combat buffs are read in three places, one per stat**: `playerAttackPower` reads `buffs.attack`, `playerDefensePower` reads `buffs.defense`, and `combatSpeed()` reads `buffs.speed` for `dodgeChance` and `attemptFlee`. That third one was missing — `castSpell()` had always written Haste's `{ speed: 5 }` and nothing ever read it back, so Haste was a 14-mana spell with no effect. All three still clamp to their own ceilings (50% dodge, 60% block, 90% flee), so a buff helps up to the cap and no further. Note this module deliberately never imports `state/persistence.js`: permadeath only sets a flag, and `ui/screens/defeat.js` does the deleting (see the import-time DB gotcha above).
- `data/travel.js` — `beginTravel(state, exit)`/`tickTravel(state)` for timed travel: sets up `state.currentTravel`, ticks it once per game-loop second, and on completion moves `state.currentLocationId` and clears itself. **`travelSecondsFor(state, baseSeconds)` shortens the trip by the speed skill** — 0.4% a level from a base of exactly 1.0 at level 1, floored at 0.6 (40% off, reached around level 101) and `Math.ceil`ed. Gentle and ceil-rounded on purpose: the integration tests drive a real game through `tmux` with a level 1–5 character, so anything steeper would silently change the times they wait on. `currentTravel` carries **both** `baseSeconds` (the exit's authored `time`) and `totalSeconds` (what you actually walk), because the XP grant uses the **base**: paying on the shortened figure would make every level of speed cut the xp that speed earns, a skill that taxes its own training. `ui/screens/traveling.js` counts down `totalSeconds` and needs no change; `ui/screens/travel.js` never displays exit times, so nothing advertises a figure the walk then beats.
- `data/worldMap.js` — builds the travel map that `apocylta-guide.md` carries between its `worldmap:begin`/`worldmap:end` sentinels. Every location declares a **`region`** (nine of them, listed in `REGIONS` with a `name` and a `root`); `buildRegionTree(regionId)` walks BFS from that root **in two passes** — overland exits (`path`/`cave`/`in_cave`/`shop`) plus `HUB_FEATURES[].to` links first, then teleports and airboats for whatever is left. The split is the whole point: a single-pass walk files `mountain_peak` and `cave_entrance` under `portal_room`, which is topologically true and useless as a map, and the hub-feature edges are what reach `safehouse`, which no exit anywhere points at. Locations that are the target of a `category: "shop"` exit never get a tree row — they collapse into the region's `Shops:` line, which also drops any `HUB_FEATURES` entry carrying a `message` (those are "not implemented yet" stubs, and a player guide listing them is lying). `crossRegionLinks()` feeds the overview diagram, whose fan centres are **found by counting**, never named: `playerhome` went from 2 cross-region exits to 5 in one sitting. `tools/buildGuideMap.js` (`npm run docs:map`) does the splicing — `data/` stays free of filesystem work the same way it stays free of `ui/` imports — and `test/unit/worldMap.test.js` asserts the committed block is byte-identical to what this builds, so forgetting to regenerate fails the suite instead of leaving the guide describing a world that moved.
- `data/shops.js` — `getBuyPrice`/`getSellPrice`, `getBarterXp`, `isPurchasable` gated by barter skill level. **Every `ALL_ITEMS` entry carries a literal `value` in base units**, so the `BASE_BUY_PRICE * rarityLevel` fallback is unreachable for a real catalog entry and survives only for the bare shapes callers build by hand. Rarity now sets the *band* (`RARITY_BANDS`) and the item's own power sets where in it the price lands. `SELL_FRACTION` is exported so `test/unit/economy.test.js` can derive its craft ceiling (`1 / SELL_FRACTION` = 2.5) rather than hardcode it: **no recipe whose ingredients are all purchasable may output more than 2.5× their cost**, which is exactly where buy-craft-sell starts minting money. Sixteen recipes crossed that line under the old rarity-only pricing (`herbal_tea` and friends paid 5×); the pass closed all sixteen and cut value-destroying recipes from 40% to 15%. The reverse bound ("crafting from gathered mats stays profitable") is deliberately **not** asserted — `steel_chestplate` is tagged `uncommon` while eating four steel bars, and every `iron_*` piece has the same shape, so it can't hold without retagging the gear. Most shops declare `types` and are rendered by `shopBuy`; `shop_housing` and the two black-market shops instead carry a `screen` override, which is the whole mechanism routing them elsewhere (`location.js` does `shop.screen ?? (mode === "sell" ? "shopSell" : "shopBuy")`).

**The Black Market** (`BLACKMARKET` in `item_backbone.js`, `ui/screens/blackMarket.js`) is the one shop that sells out of something other than `ALL_ITEMS`. It has two collections, each a map of sections, each section optionally carrying a `global` block — so **everything iterating one must strip the `global` key** or it renders as a purchasable row. `shop_illegal` sells `illicit_goods` (three sections of hand-priced named items) and `shop_enhancements` sells `enhancements` (five tiers × 14 skills). Points worth knowing:

- **`BLACKMARKET_CATALOG`** is to the enhancements what `FISHING_CATALOG` is to fishing, and for the same reason: they're authored with a `type` of `charm`/`talisman`/`beads`/`ring`/`bangle`, none of which `ITEM_TYPES` knows. `withBlackMarketDefaults()` translates them once into `type: "enhancement"` (a type of their own — riding `magic` would put all 70 into the magic shop's stock and `rollLootByType`'s magic pool), keeps the authored vocabulary as `enhancementSlot`/`enhancementGroup`, sets `rarity` by tier and `value` from the authored `cost`. The 70 enhancements are **exempt from `RARITY_BANDS`** — their hand-set 1k–500k ladder *is* this shop's gate (there's no barter gate here, see below), so banding them would flatten the whole storefront.
- **An illicit_goods entry is not always an item.** The two named sections use their own key as the item id; the smithing bundles are names for piles of something else and hand over their `outputs` instead. `blackMarketGrants(id, entry)` is the one place that distinction lives, and it takes the id separately because only illicit_goods entries carry a `key` field.
- **A section's `global.keyRef` is documentation, not a lookup route.** The screen resolves through `ALL_ITEMS`. Two of the three blocks named the wrong catalog before anything read them, so `test/unit/blackMarket.test.js` pins each section's ids against the catalog(s) its `keyRef` names.
- **No barter gate here, deliberately.** Every entry is mythic/unique/godlike, so `isPurchasable` would show an empty shop until barter 65 and hide the rings and bangles until 100. The 1k–500k hand-set price is the gate, and rows colour green+bold when affordable, red when not (`colorTag`'s bold survives `colorize: 0`, so the distinction holds in monochrome). Group headers are emitted **only where they collapse something** — one group means the tab strip already said it, and all-singleton groups (every enhancement tier is one entry per skill) would turn 14 rows into 28 in a pane that holds ~18.

**Worn enhancements actually apply**, through one choke point. They equip into `state.enhancements` — five slots keyed by tier, kept separate from `state.equipment` because the enhancement `ring` tier and the armor `ring` slot are different things. `equipItem()` routes between the two maps **on the item's type, not the slot name**: a name-based check filed `ring_of_eternity` as an enhancement and let a Luck Ring evict it. `effectiveSkillLevel(state, skillId)` = trained level + the sum of `effect[`${skillId}Up`]` across the worn five + `aidBonus()` (the Blessed spells — see below), deliberately **not** clamped to `MAX_SKILL_LEVEL`. Use it wherever a level *gates or scales* play (combat maths, mining/fishing/magic requirements, gather odds, shop stock); **never** where the level is the thing being measured — `data/quests.js`'s `learnSkill` objective, `data/achievements.js`'s `learnSkill` req, xp grants, the action screen's session delta and every display read the trained level, since a 1000gp charm must not complete "reach mining level 10". Persistence reuses the long-empty `enhancements` table (no `ALTER TABLE` needed, same as `achievements`) and stores **only item ids** — the slot is a property of the item, so the map rebuilds itself on load and can't drift from the catalog.
- `data/stations.js` — derives `STATION_RECIPES` by reading each recipe collection's own `global: {station, skill}` block in `item_backbone.js`. **This is the codebase's one explicit "add data, not code" extensibility point**: a new recipe collection needs only to be listed in `COLLECTIONS`. Two collections may name the **same** station — `COOKING_RECIPES` and `FISHING_RECIPES` both cook at `cooking_station`/`campfire` — so the derivation **merges** into the existing entry, mutating its `recipes` object in place rather than assigning (plain assignment silently dropped whichever collection registered first, and rebuilding the object instead would break the shared-pool identity `cooking_station` and `campfire` rely on). `playerhome` is the one location whose stations come from `state.ownedStations` instead of static `hubFeatures`.
- `data/hubFeatures.js` — `HUB_FEATURES`, non-travel location amenities, each with a globally-unique `hotkey` and either a `to` (location transition), a `screen` (e.g. `quest_board` → `"questBoard"`), a shop link, or a stub `message`. Note `"q"`/`"Q"` can never be used here — `main.js` binds a global hard-quit on those keys that fires independently of the screen-level keymap.
- `data/items.js` — **the one place a consumable is consumed.** `consumeEffectOf(itemId)` (the classifier, symmetric sibling of `item_backbone.js`'s `equipSlotOf()` — id → `{kind, amount?, stat?, targets?}` or `null`) and `useItem(state, itemId, ctx)`, where `ctx` is `{target, combat}` supplied only by combat. Both the backpack's `U` and `data/combat.js`'s `usePotion()` (now a thin wrapper) route through `useItem`, so `item_backbone.js`'s `CONSUME` economy — skill xp plus whatever the thing came in — applies wherever a consumable is used; same "one hook where it actually happens" reasoning that keeps `recordSpellCast` inside `castSpell()`. Two things to know: food is gated on `health_boost` being present, not on `type === "food"`, because the ten `subtype: "ingredient"` foods (flour, yeast, dough) are crafting inputs; and `useItem` returns `{used, message}` rather than the `string | null` of `learnSpell`/`castSpell`, because every refusal here has a distinct reason (full health vs. not poisoned vs. not usable) and callers shouldn't have to guess. `cure` items always refuse — the player carries no status effects for one to remove. `revive` refuses off the backpack too, because it isn't used on purpose: `attemptRevive(state)` is the **pre-death hook**, called from `resolveRound()` the instant `state.hp <= 0` and *before* `resolveDefeat()` (which is what permadeath hangs off, so intercepting earlier is what saves the run). It spends the weakest revive in the backpack — `revive` is a *subtype*, so a revive potion qualifies as readily as the aid item — and returns `null` when there's none, leaving the caller to die as it would have. A bare `revive: true` restores fully; a numeric `revive` is read as a fraction of `hpMax`.
- `data/toolbelt.js` — **what you can carry, in three containers that fill independently**. Two are weighed: the **toolbelt** (`storeIn: "toolbelt"` items — scrap, tools, bait and hooks) against `toolbeltWeightCap`, and the **backpack** (everything else) against `backpackWeightCap`. The third is the **potion pouch**, which still counts *slots* and is keyed off `type === "potion"` rather than off `storeIn`, so a potion costs one slot however many you stack and no weight in either weighed container. `weightRoomFor(state, itemId)` answers "how much more of this fits" in the item's own container (`Infinity` for a potion, whose limit is slots — `potionSlotsFree` handles those), and `loadFraction` returns the fuller of the two weighed containers, which is what `data/flavor.js`'s `packLine` bands off. This replaced a slot count that measured **distinct item ids**, so 5000 logs cost what one log did and tools were free because nothing had a budget to charge them against. Both weight budgets get `+2 per effective strength level`, read through `effectiveSkillLevel` so a Strength Charm or a blessing lifts them too — which is why **this module imports `state/gameState.js` while gameState imports it back**. That cycle is deliberate and safe for the same reason the `data/magic.js` ↔ `data/quests.js` one is: both sides export only hoisted function declarations and do no work at module-evaluation time. Belt/backpack budgets take the **larger**, never the sum. `hasBeltEquipped`/`slingshotAmmoCap`/`waterBottleCap`/`quiverCap` are unchanged and stay **outside** the weight system — they're plain counters on `state.toolbelt` with their own caps, so a full water bottle costs no toolbelt room (`quiverCap` can be `Infinity` — see the JSON-encoding note in `server_backbone.js` below).
- `data/flavor.js` — ready-made `flavorText` entries: `timeLine`/`indoorTimeLine` (dawn/morning/afternoon/dusk/night), `weatherLine`, `openLine` (reads the location's `openHours`), `firstVisitLine`, `dangerLine`, `healthLine`, `packLine`. Each is `(state, location) => string | null`, and the `null` is load-bearing — it's how a line appears only when it has something to say (so a helper must return bare `null`, never `styled(null)`, which would render the word "null"). **Lines carry meaning in their colour**, all of it via `markup.js`'s `styled` so the `colorize` setting still governs: time/weather recede into grey as ambient scene-setting, `dangerLine` is green/red, `healthLine` bands through the *same* `HP_BANDS` the status bar's HP number uses so the two can never disagree, `packLine` deepens amber→red as it fills, `firstVisitLine` is gold only on the new-location branch, and `openLine` names its hours on **both** branches (green "Open until 8pm" / red "Open 8am - 8pm") — the open case used to say nothing at all about when the shop shuts. **Weather is derived from the clock, not stored**: hashing the day and a ~4-hour block gives something that holds steady, drifts on its own, and survives a reload with no state, no transitions and no save migration. **This file must not import `state/gameState.js`** — gameState imports `data/locations.js`, which imports this, so that would close the loop; the day-wrapping clock maths it needs lives in the leaf `state/clock.js` instead (which also de-duplicated the two copies gameState was carrying).
- `data/mining.js` — `mineableOres(locationId?)`, `canMineOre(state, oreId)`, `rollMineBonuses(state, rng?)`. Two independent gates: **which ores exist here** (the location's `mine` tier, via `item_backbone.js`'s `MINE_LOCK`/`isMineableAtTier`) and **whether you can mine one** (mining skill level plus equipped pickaxe tier — so every level in `SKILL_BLOCKS.mining.ores` needs a pickaxe in `.tools` that can reach it, or the ore is listed and permanently unmineable). Tiers are **cumulative** — a `mid_tier` mine yields everything `basic` does plus its own — and an ore listed in *no* tier is unlisted rather than forbidden, so it shows everywhere (otherwise adding an ore item would silently make it unmineable until someone filed it under a tier). `MINE_LOCK` keys `metals` by item **subtype** but `gems`/`fuel` by item **id**, because every gemstone shares the subtype `"gemstone"` and every fuel `"fuel"`; `isMineableAtTier` matches either. Omitting `locationId` applies no gate at all.

  **There are five tiers** — `basic`(1)/`mid_tier`(2)/`advanced`(3)/`high_tier`(4)/`legendary`(5) — ordered by the mining level their metals need (tin/copper 1, iron 5, cobalt 10, mithril 25, syllic 40, adamantite 45, runite 60). `advanced` exists because nine locations (the Cordura deep mines) had always declared it while `MINE_LOCK` had four keys: `getMineLockByName()` was a **switch mirroring the object**, `"advanced"` hit its `default: return null`, and `mineableOres()` reads a null lock as *no gate* rather than *no ores* — so those nine mines quietly handed out every ore in the game, runite included. Both helpers are now plain lookups off `MINE_LOCK` so they cannot fall out of step with it, `test/unit/locations.test.js` asserts every location's `mine`/`water` value is one the catalogs know, and `tier` numbers must stay **contiguous from 1** because `mineLockNamesUpTo()` walks them as a range whose ceiling is the key count. Splitting `syllic` off `high_tier` into `advanced` cost the tiers above nothing, since tiers are cumulative — the only behaviour that changed is the nine broken mines tightening from 9 ores to 7.
- `data/fishing.js` — the same shape as `data/mining.js`, for the `fish` action: `catchableFish(locationId?)`, `canCatchFish(state, speciesId)`, `equippedRodTier`, `fishingGearFor`, `spendBait`. Two gates again: **which species are here** (the location's `water`, against `FISH[].water` — where **`water: true` means both waters**, so such a species shows up wherever there's water at all) and **whether you can take one** (fishing level against `SKILL_BLOCKS.fishing.catches[difficulty]`, an equipped rod whose `SKILL_BLOCKS.fishing.tools` tier reaches that same level, and — for anything not caught on the rod alone — the bait/net/hook in the backpack). Both rod ladders count, the metal rods in `ITEMS` and the `basic`→`godlike` rods in `FISHING_ITEMS`, because the check matches the canonical subtype `"fishing rod"` they share; an equipped rod missing from `.tools` defaults to tier 1, same convention as mining's untiered starter pickaxe. **Bait is spent per catch, nets and hooks are not** — `spendBait` deliberately calls `removeItem` *without* `{ force }`, because bait is a cost, so godmode/`adminInfinite` make it free (the same rule `useItem`/`spendIngredients` follow). Species whose catch items don't exist are filtered out rather than offered, so a half-added species can't start a gather that yields nothing. Omitting `locationId` applies no gate at all.
  **Coal and gemstones are not selectable ores** — `mineableOres` filters both subtypes out, and `rollMineBonuses` drops them as separate per-roll extras on top of the chosen ore (called from `state/gameLoop.js` when the action is `mine`). They have to be rolled here rather than folded into `lootSubtype`, for two reasons: `rollLootByType` matches on subtype, so the literal `"gemstone"` would let a tier-1 mine yield a legendary diamond — hence its `allowIds` parameter, appended fifth so `data/combat.js`'s positional `undefined, undefined, rng` call still works; and sharing one pool meant fuel's four `common` items outweighed the single ore 4:1. `rng` is injectable because the game loop's roll block has no unit coverage.
- `data/quests.js` — `visibleQuests`/`startedQuests` (level+lock gated listing / the player's own accepted quests), `objectiveStatus` (per-objective `{current, target, complete}` — most objective types are computed live off existing state; `sellItem`/`craftItem` are the two exceptions, tracked via small event counters since they can't be reconstructed from current state alone. A known type written in a shape it doesn't implement — `learnSpell: { rarity: "legendary" }` where a spell-id array is expected — returns the `UNSUPPORTED` zero-progress status rather than throwing: **every quest screen renders every objective of every quest**, so one malformed entry used to hard-crash the Journal, Quest Board and admin editor. It reads as stuck at 0/1, which is the signal to fix the data), `acceptQuest`/`completeQuest`/`claimCompletedQuests`, and the event hooks `recordItemSold`/`recordItemCrafted`/`recordSpellCast`/`recordEnemyDefeated` (from `shopSell.js`, `stationCraft.js`, `data/magic.js`'s `castSpell()` and `data/combat.js` respectively). **Objectives are addressed by a `::`-joined path** (`"Defeat The Mad Bert Brothers::Defeat Hubert"`), which is also the key `objectiveProgress`/`adminForced` use — both persist as arbitrary-keyed JSON, so nesting needed no save migration, and it's the same separator `adminQuests.js` already put between questId and label. `walkObjectives(quest)` yields `{path, label, def, depth, optional, group}` for every node, and **every hook and screen iterates that rather than `Object.keys(quest.objectives)`** — a counter-backed objective nested in a group is invisible to anything that doesn't, and would sit at zero with nothing to explain it. `resolveObjective(quest, path)` is the lookup half. Each hook also bumps the matching `state.lifetime` ledger, because its per-quest counter only fires for quests that are currently `in_progress` — with no matching quest accepted the event would otherwise be recorded nowhere, which is no basis for an achievement. Note `recordSpellCast` lives inside `castSpell()` rather than at its call sites: it used to be called only from the spellbook screen, so every spell cast in combat went unrecorded.

### State/engine layer (`state/`)

- `gameState.js` — `createInitialState()` defines the full mutable state shape (hp/mp/`cur`/level/xp, `currentLocationId`, `clock.totalMinutes`, `inventory`/`skills` maps, `equipment`, `toolbelt`, `currentAction`, `currentTravel`, `currentCombat`, `enemiesDefeated` (the lifetime `{enemyId: count}` tally behind `defeatEnemy` objectives), `saveSlotId` (which slot the session is bound to, so permadeath knows what to delete — set by `ui/screens/saveSlots.js` on both save and load), `achievements` (`{id: {unlockedAt}}`, key presence *is* the unlocked flag), `locationsVisited` Set, `lifetime` (`{sold, crafted, cast, used}`, id-keyed so achievements' by-type/by-subtype shapes derive through `ALL_ITEMS`/`SPELLS`; `used` is written by `data/items.js` but no objective/`req` type reads it yet — adding a ledger key also means adding it to `state/persistence.js`'s hardcoded load-side list, since the save side iterates generically and would otherwise drop the rows silently on load), `toasts`, `quests`, `currentScreen`/`returnScreen`/`menuOrigin`, `characterDraft`, `ownedStations` Set, and the three session-only switches `adminInfinite`/`adminAutoAchievements`/`godmode`, the last seeded from `player_config.godmode`). `equipment` carries all 13 slots including `shield`/`cloak`/`ring`/`necklace` — those four used to be missing or dropped on save even though 23 catalog items equip into them. Also `moveTo(state, locationId)` — **the single choke point for changing location**, so `locationsVisited` can't drift; everything that moves the player (travel completing, an instant exit, a hub feature, a teleport spell, the defeat respawn) goes through it rather than assigning `currentLocationId` directly. And `pushToast`/`activeToast`, whose expiry rides on `clock.totalMinutes` (already advanced once per tick) rather than a second timer.

  **Aid spells (the Blessed line) live here too**, as `state.aidBuffs` — `[{ spellId, untilMinutes }]` and nothing more, since `aidSkillBonuses()` re-derives the magnitudes from `SPELLS` on every read, so retuning a spell can't leave a stale bonus baked into a save. `applyAidBuff` **replaces** an entry of the same spell rather than appending (a recast refreshes the clock instead of doubling the bonus; two *different* blessings still stack, which is the point of the godlike ones overlapping the rare). `activeAidBuffs` prunes expired entries as it reads and `aidBonus` sums what's left — both copying `activeToast`'s trick of riding `clock.totalMinutes`, which is why **neither needs a tick hook**: whoever asks gets a correct answer however they got there, including screens that never re-render. The bonus is folded into `effectiveSkillLevel` rather than into each consumer, which is the whole design: one seam means a blessing reaches every gate and every scaling factor and reaches no quest, no achievement and no readout, without any of them knowing blessings exist. Persistence reuses the long-empty `buffs` table — third time that's paid off after `achievements` and `enhancements`, and again no `ALTER TABLE` — storing the **remaining** minutes, never an absolute deadline: `clock.totalMinutes` is *not* persisted (`createInitialState` reseeds it to 7:38pm), so a stored `untilMinutes` would be measured against a different origin on every load. `state/autosave.js` mirrors that exactly. **The purse is `state.cur`**, four coin counts (`copper`/`silver`/`gold`/`syllic`) replacing the old single `state.gold` integer, with `walletTotal`/`addCurrency`/`canAffordCurrency`/`spendCurrency` as the only writers — the same "one choke point so the godmode carve-out is visible" reasoning as `addItem`/`removeItem`, and `canAffordCurrency`/`spendCurrency` must keep agreeing about godmode or a purchase is refused before the free spend can run. **Holdings are independent, not canonical**: you keep the coins you were given, so being paid 100 in syllic leaves one syllic coin, and `formatCurrency(state.cur)` can differ from `formatBase(walletTotal(state))` — 100 copper coins read as "100 copper" while being worth "1 syllic". `spendFrom` spends smallest-first and breaks the *smallest* coin large enough only when the small change runs out, giving canonical change back; every metal divides evenly into the ones below it, so a break can never strand a remainder. Money **set** rather than earned (a starting character, the post-death reset, the admin editor) goes through `purseFromBase` instead, because nobody is handed 5500 copper coins. Also holds pure(ish) mutators: `addItem` (**takes what fits and returns the amount taken, 0..qty** — not a boolean. A pack with room for two of the three ore you just mined gives you two rather than voiding the haul, and `state/gameLoop.js` reports what actually landed. Unlike the slot-counting version it replaced, **every** add is checked, not just the ones opening a new id: under weight, stacking more of something you already carry costs exactly what the first one did. Godmode skips the limit entirely, matching `removeItem`'s carve-out. It's also the one hook where **strength xp for hauling** is granted, so it covers every way items arrive — mining, loot, crafting, the shop counter)/`removeItem` (capacity-aware, belt-gated via `data/toolbelt.js`; `removeItem` takes a fourth `{ force }` option — see the godmode note in the Admin section for which callers pass it and why), `equipItem`, `grantSkillXp` (applies proficiency + difficulty multipliers, loops level-ups against `skillLevelCost` up to `MAX_SKILL_LEVEL`, and — per level gained — grants `PLAYER_XP_SHARE_PER_SKILL_LEVEL` of `skillLevelCost(newLevel)` as **player** xp via `grantPlayerXp`; xp past the skill cap still accumulates, since it's what the action screen's session delta is measured against), `grantPlayerXp` (the overall player level, on `playerLevelCost` and capped at `MAX_PLAYER_LEVEL` — **the raw pool adder**, so what it's handed goes straight in), `grantRewardXp` (**the entry point for flat rewards** — combat kills and the group bonus, `completeQuest`, `grantAchievementReward` — multiplying by `playerXpScale(state.level)` so a 1000-xp quest is worth a comparable slice of a level at 100 as at 10, where flat would be 0.09%. `grantSkillXp` must keep using `grantPlayerXp` directly: scaling that too would compound the curve against itself and undo the rescaling), `finalizeCharacter(state, draft)` (converts the character-creation wizard draft into a real character), and `formatClock`/`isSafeZone`/`isLocationOpen`.
- `gameLoop.js` — `startGameLoop(state, onTick)`, a 1-second `setInterval` tick: advances the clock; while an action is running, increments `elapsedSeconds` and every **`gatherTimeFor(state.difficulty)`** seconds runs `resolveGatherAttempt(state, rng)` (exported, so the pacing logic has unit coverage the `setInterval` itself can't) — that charges `spendBait` for `fish` first (a miss costs bait too; running out clears `currentAction` and toasts, leaving `ui/screens/action.js`'s `render()` to re-route the way `traveling`/`combat` already do), then rolls the attempt: **a miss takes nothing and pays no XP at all**, a hit takes loot (passing `currentAction.lootIds` through `rollLootByType`'s `allowIds`) and grants `SKILL_XP_PER_GRANT = 5`. Either way it pushes a line onto `currentAction.attempts`, a rolling window of the last 5 that the action screen renders. Mine bonuses roll only on a hit — they're extras on top of an ore, not a consolation prize. **The ambush roll has its own cadence**, `encounterTicFor(state.difficulty)` (`logic.actionTic`), rather than riding the gather: when the two shared one, slowing gathering down made the game safer, and made the *hardest* difficulties the safest of all since they wait longest between attempts; while `state.currentTravel` is set, calls `tickTravel(state)` (`data/travel.js`). Also exports `shouldAmbush(state, rng)`, which on that same `actionTic` cadence (10/5/3/2/2/1/1 seconds from casual to demon_lord) can interrupt a gather in an unsafe zone with a real encounter. Calls `onTick(state)` after every mutation so the caller (`main.js`) decides how to re-render — the screens needing a per-tick re-render are `"action"`, `"traveling"` and `"location"` (the last because `data/flavor.js`'s lines are computed per render, so a line about dusk would otherwise sit frozen until the next keypress); **combat is turn-based and deliberately needs none**. Because the loop has no `ui` handle, an ambush only sets `state.currentCombat`, and `main.js`'s `onTick` does the actual `switchScreen` to `"combat"`.
- `persistence.js` — **multi-slot** save/load. Two things bite when adding fields: `db_backbone.js`'s `CREATE TABLE IF NOT EXISTS` never adds a column to an existing database, so a new column needs an explicit `PRAGMA table_info` + `ALTER TABLE` migration beside the ones for `saved_at`/`quest_objectives_json`/`health_max`/`mana_max` (covered by `test/unit/dbMigration.test.js`, which seeds an old-shape DB — a fresh-schema test passes off `CREATE TABLE` alone and proves nothing). And `quest_objectives_json` now holds a `{progress, adminForced}` envelope; a parsed object with no `progress` key is read as a legacy bare progress map, so "progress" must never be a real objective label. The purse rides four `cur_*` columns added beside the legacy `gold` one, which is **left in place and no longer written** — SQLite can't drop a column without rebuilding the table, and `db_backbone.js`'s migration converts the old total into coins exactly once (guarded on `cur_copper` being absent, so it can't fire twice; and on `gold` existing at all, since a database old enough to predate that column would otherwise throw on the SELECT and take the import down with it). Note `cur_gold` is a *count of gold coins* while the old `gold` was an undenominated total — the names do not say that, so the schema comments do. Save/load via `better-sqlite3` prepared statements in an explicit transaction: `saveGame(state, slotId)`/`loadGame(slotId)`/`deleteSave(slotId)`/`listSaveSlots()` (slot ids `1..game_config.saveSlots`). Child tables (inventory/proficiencies/stations/spells/quests/enemies_defeated/achievements/locations_visited/lifetime_counters) are deleted and rewritten wholesale each save — no diffing. The long-unused `achievements` table needed no `ALTER TABLE` migration: unlocking is binary and progress is always recomputed from live state, so its existing columns suffice. `state.currentAction`/`state.currentTravel`/`state.currentCombat` are intentionally never persisted — loading always resumes idle and out of combat. **The stored `level` column is not trusted on read**: `loadGame` and `listSaveSlots` both derive it from the banked `experience` via `playerLevelFromXp` (as does `state/autosave.js`'s `readAutosave`), which is what migrates saves written against the old, far shallower player curve — nothing is discarded, the same xp just buys fewer levels. The column is still written, so it stays readable by anything that wants the raw value.
- `autosave.js` — a single JSON snapshot (`AUTOSAVE_PATH`, default `data/autosave.json`), separate from the numbered SQLite slots: `writeAutosave`/`readAutosave`/`autosaveSummary`. Written on a timer in `main.js` (`game_config.autosaveInterval` seconds), and offered as an extra loadable entry (not a numbered slot) in the save-slot picker.

### UI layer (`ui/`) — hand-rolled screen router over neo-blessed

Each screen in `ui/screens/*.js` (34 files, plus 9 more under `ui/screens/admin/`) is a plain object implementing the same contract, registered via `registerScreen(name, screen)` in `main.js`:

```js
{
  keymap: { <UPPERCASE_KEY_OR_"ESCAPE">: (state, ui) => { ... } },
  subHeader?: string | fn | Array<string | fn>,   // (state, location) => string | null
  onEnter?(state, ui),
  onExit?(state, ui),
  render(state, ui),
}
```

**`subHeader`** opts a screen into the second header bar — a line of flavour under the main header, currently on 13 screens: `questBoard`, `mineSelect`, `fishSelect`, `backpack`, `toolbelt`, `spellbook`, the three shop screens and the two workbench screens (`stationSelect`/`stationCraft`). It takes the **same shapes as a location's `flavorText`**, and entries get `(state, location)`, so `data/flavor.js`'s helpers drop straight in. `ui/router.js` resolves and applies it in `renderCurrentScreen` **before** the screen renders, so a list sizes to the height it'll actually have; screens never touch the widget. Two things worth knowing:

- **The line is picked by the hour, not at random.** These screens re-render on every keypress, so a random pick would make the bar flicker as the cursor moves. `null` entries drop out first, so a conditional helper simply doesn't take a slot.
- **It costs 3 content rows while shown** (21 → 18 at 120x40), and `ui/subHeader.js`'s `applySubHeader` is **the only place in the codebase that changes widget geometry at runtime**. `mainContent` and `inventoryList` are siblings pinned at the same `top`/`height`, so both move together — moving one leaves a gap or an overlap depending which screen is up. Screens that don't opt in pay nothing, which is why `menu` (already overflowing its pane) is untouched.

- `ui/router.js` — `switchScreen(state, ui, name)` calls `onExit` on the outgoing screen, sets `state.currentScreen`, then calls `onEnter` + `render` on the incoming one. `handleKey` is the single `screen.on("keypress", ...)` handler wired once in `main.js`; it uppercases the pressed key (or maps Escape/Left/Right to named tokens), looks it up in the current screen's `keymap`, runs the handler, then re-renders.
- `ui/layout.js` — `buildLayout()` builds the fixed blessed widget tree: a 3-column header (`headerLeft`/`headerCenter`/`headerRight` — title+name+level+location+gold, current action name or `[idle]`, and a right-hugging clock), a status bar, a content pane, and a command box, plus hidden text inputs for name entry. Forces `terminal: "xterm-256color"` on the blessed screen — neo-blessed's terminfo lookup otherwise under-detects color depth for several common `TERM` values (confirmed for `tmux-256color`), silently degrading every hex color tag to a crude 8-color approximation. `renderChrome()` renders the shared header/status bars on every screen, with color throughout: a bold blue title, the player's name bold white with `Lv.N` beside it (via `headerIdentity()`, which **omits the whole segment when `state.name` is null** — the header draws on the title screen and every creation-wizard step too, and truncates long names so they can't push `gp:` off the 50%-wide column; `app_version` moved to the title screen when this took its place, and `ui/screens/title.js` is now its only consumer), the location name bracketed in green/red by safe-zone status, gold/location name in a yellow-orange, HP/MP bolded and percentage-banded (green→white→blue→orange→red for HP, light-blue→blue→dark-blue→red for MP), and — while an action is running — a percentage-banded XP progress bar (`formatXpBar`/`actionProgressText`, white→blue→yellow→green→gold, bold from yellow up). An achievement unlock toast (gold, bold) takes that same tail slot while live: unlocks can happen on any screen, including ones that never render `state.lastMessage`, so they ride the one bar every screen draws. A gold `[ BLESSED ]` badge sits beside the `[ GOD ]` one while any aid spell is running, for the same reason godmode has one — a blessing silently changes what you can mine, catch and buy on every screen. Both `activeToast()` and `activeAidBuffs()` are called from **render**, not from the tick, since both expire their own stale entries as they read.
### Settings (`state/settings.js` + `state/displaySettings.js` + `ui/screens/settings.js`)

Menu → `[T]`. Backed by `game_settings`, a **single row at `id = 1`** (settings belong to the install, not a character), bootstrapped on first read rather than by a migration. Two columns are live — `colorize` and `action_key` — plus the `first_run`/`last_run`/`last_autosave` stamps; the rest of the table (`terminal_*`, `dev_*`, `account_id`) is deliberately untouched.

- **Two layers, and the split is load-bearing.** `state/displaySettings.js` imports **nothing** and holds the live copy; `state/settings.js` owns the DB row and pushes into it. `ui/format.js` reads only the former, because it's imported by 39 of the 40 screen files and by `renderChrome` — pointing it at the DB module would drag `db_backbone.js`'s import-time SQLite open into `format.test.js`/`layout.test.js`/`spellbookScreen.test.js`, all of which import it statically. Reads also can't hit the DB per call: `colorTag` fires dozens of times per render and `renderChrome` runs every second.
- **`action_key` styles**, via `formatCommandCell`: `B` boxed key (`[T]ravel`, the default and the pre-settings behaviour), `P` prefix (`[T] Travel`), `R` bolded (`{bold}T{/bold}ravel`), `S` boxed action (`T: [Travel]`). Only `R` needs a fallback — with the hotkey nowhere in the label there's no letter to embolden, so it uses the prefix form. That isn't an edge case: `<>`, `+-`, `123`, `1-7` and every digit-keyed row on the location and travel screens hit it. **`R` emits markup inside a padded cell**, so `formatCommandRow` pads on the tag-stripped length; padding on raw length throws the legend out by 13 characters per cell.
- **`colorize: 0` drops colour but keeps `{bold}` and `{underline}`**, and leaves `inventoryList`'s `inverse: true` alone — all three are video attributes (SGR 1 / 4 / 7) that render on a monochrome terminal, and inverse is the *only* selection indicator on 12+ list screens. The gate lives in `markup.js`'s `styled()`, so nothing may emit a raw `{...-fg}` tag; `renderChrome` had five that had to be routed through it.
- **The `B` default is deliberate**: 8 integration tests `waitFor` strings like `"[S]ave"`, and they time out rather than fail fast if the format shifts under them.
- **`game_settings` shipped unusable.** It declared `FOREIGN KEY(account_id) REFERENCES player(id)` with `account_id TEXT NOT NULL DEFAULT ''` against an INTEGER `player.id`, and better-sqlite3 enables `PRAGMA foreign_keys` by default — so every insert died with "FOREIGN KEY constraint failed". That's why the table had zero rows. `db_backbone.js` now rebuilds the table without it (SQLite can't drop a constraint in place) and backfills `action_key`; both migrations only ever fire on a pre-existing database, so `test/unit/dbMigration.test.js` seeds the old shape to reach them.

- `markup.js` (top level) — **the one place blessed's `{green-fg}`/`{/green-fg}` markup is built.** `styled(text, { color, bold, underline })` is the gate; `bold()`/`underline()` are shorthands and `colorTag(text, color, bold)` is the original three-arg form, kept byte-identical because ~39 screens and `renderChrome`'s eight call sites use it. Also `visibleLength`/`stripMarkup`, and the `COLOR` palette + `pickBand`/`HP_BANDS` (moved down from `ui/layout.js`, which imports them back). It sits at the top level, importing only `state/displaySettings.js`, because **`data/flavor.js` needs it and nothing in `data/` or `state/` may import from `ui/`** — top-level leaves are already the shared layer (`logger.js`, `config.js`, `item_backbone.js`). `ui/format.js` re-exports the lot so existing importers were untouched.

  **`COLOR` entries are 256-palette indices, never hex.** A hex tag goes through neo-blessed's `colors.match()`, whose nearest-colour search fails silently — `#ffd700` gold resolved to index 3, a dull `(205,205,0)` olive, as did every grey and amber tried, while `#ffa500` resolved fine. An index skips that search and takes the identical code path after it. `orange`/`yellowOrange`/`darkBlue` are the exact indices their old hex values resolved to (so they look unchanged); `gold` moved to 220, the colour it always asked for. `test/unit/markup.test.js` pins this.

  Styled spans **nest correctly** — `_parseTags` keeps separate fg/bg/flag stacks and re-emits the enclosing entry on a close — which is what lets a flavour line style one word of itself and still sit inside `ui/subHeader.js`'s white wrap.
- `ui/format.js` — `formatCommandRow()` turns `{label, hotkey}` lists into the aligned `[T]ravel | [L]ook for food | ...` legend (see `apocylta-gui.md` for the intended visual layout of each screen). Also **`wrapIndented(text, { width, indent, hangingIndent })`**: blessed wraps by itself but only ever back to **column zero**, which dropped a long flavour line's tail flush against the pane border. Pre-wrapping to a width *narrower* than the pane makes blessed leave the rows alone — emit anything wider and it re-wraps and undoes the indent, so `width` must be the pane's real inner width (`ui.screen.width - 2`, read per render so a resize is followed). Note tags inflate string length, so any `padEnd`, wrap or row count has to be computed on `visibleLength` — `test/unit/locations.test.js`'s pane-overflow guard now calls the real `wrapIndented` rather than approximating with `Math.ceil(line.length / width)`, which both counted tags as content and assumed a character split where the screen breaks on words. `inventoryList`'s `selected: { inverse: true }` style turns a colored row's foreground into its background while highlighted.
- `ui/listScreen.js` — the screen-agnostic list plumbing (`enterList`/`exitList`/`selectedId`/`rowBuilder`/`paint`). Split out of `ui/screens/admin/shared.js` once the Settings screen needed the same movable cursor; `shared.js` re-exports all five so the admin editors still import everything from one place. **The cursor rules documented under Admin below live here**, not in `shared.js`.
- `ui/tabs.js` — `cycleTab`/`formatTabStrip`, the `<`/`>` tab strip used by `backpack`, `spellbook` and the admin editors (the last via `compactTabLabel` instead — see Admin).
- Screens: `title` (New Game / Continue, the latter opening the shared save-slot picker), `charName`/`charDifficulty`/`charStarterPack`/`charRace`/`charClass`/`charSkills` (the character-creation wizard, staged into `state.characterDraft` and finalized via `finalizeCharacter`), `location` (main hub — builds numbered actions + hub-feature hotkeys dynamically from the current location), `travel` (digit-hotkey destination picker; instant for exits with no `time`, otherwise hands off to `traveling`. Exits are numbered off an exported `DIGITS` list — `1`–`9` then **`0` as the tenth**, which `renderBody` and the keymap share so a rendered number always presses; `town_square` reached ten exits and silently lost its portal room before that, and `test/unit/travel.test.js` now pins the invariant), `traveling` (countdown + a category-specific ASCII animation — a walker along a road for `"path"`, a glider over "sky" for `"airboat"`, a cart in a tunnel for `"cave"`/`"in_cave"`, a shimmer for `"teleport"`; `buildTravelTrack` clamps the marker's position against **its own length** rather than a fixed one, since the markers differ in width and a hardcoded clamp let the longer ones render a track wider than `TRACK_WIDTH` — ticks in the background regardless of which screen is active, so its `render()` has to defensively re-route to `location` if `state.currentTravel` completed while the player was elsewhere), `action` (in-progress gathering), `combat` (the turn-based fight — one keypress resolves one round, so unlike `action`/`traveling` it needs no per-tick render; `render()` still defensively re-routes to `location` if the encounter ended while the player was on another screen), `combatSelect` (one shared Cast/Potion picker parameterised by `state.combatSelectContext.mode`, following `saveSlots.js`'s shared-picker precedent), `defeat` (the death summary — **owns the permadeath side effects**: deleting the save slot and the autosave file), `backpack` (tabbed by item type), `spellbook` (reached from `backpack`'s `C`; tabbed Learned/Unlearned, the latter sub-grouped [Learnable]/[Unlearnable] then by spell type, rows colored green/red — the only screen that colors its own content rather than leaving color to `renderChrome`. Deliberately does **not** filter by `isSpellUnlocked`: a spell above your magic level is listed with a `req: magic lv N` reason instead of hidden, and learn costs render as owned/required counts via `data/stations.js`'s `ingredientCount`), `toolbelt` (equipped tool/slingshot/belt + the three capacity lines; also the entry point to `toolSwap`/`slingshotSwap`/`journal`/`pouch`), `pouch` (**the belt's contents** — every `storeIn: "toolbelt"` item, which is the one place `storeIn` decides what a player can SEE rather than which budget it charges. Tabs by item type, rows grouped under subtype headers carrying the section's count and summed weight. `sectionOf()` keys on `subtype` **except** for the `fishing` bucket, where it falls back to `fishingType`: bait and hooks share the canonical subtype `"fishing"`, so subtype alone would lump twelve items under one heading. Exports `buildPouchRows`/`buildTabs` for blessed-free testing, like `spellbook.js` does. Note **nothing on the belt is currently consumable** — `consumeEffectOf` resolves only food/potion/aid types, and all 110 belt items are scrap/tool/crafting — so its `[U] Use` always refuses; the five `combat_aid` items read like consumables but are typed `tool`), `journal` (accepted quests, objective checklists, batch-claim rewards), `achievements` (the full catalog grouped unlocked/locked with live per-requirement progress; reached from the Menu's `A`, and one of the few screens using `inventoryList` purely for its keyboard scrolling — nothing in it is selectable), `questBoard` (level/lock-gated quest listing, Accept), `menu`, `saveSlots` (shared save/load picker used by both the title screen and the menu, with a two-press confirm pattern for overwrite/delete), `shopBuy`/`shopSell`/`shopHousing`, `blackMarket` (the storefront for both black-market shops — section tabs, affordability colouring; see the Black Market notes above), `stationSelect`/`stationCraft`, `mineSelect`, `fishSelect` (the species picker, a near-clone of `mineSelect` — but reached from the **`Fish` action** rather than a hub feature, via the action's `select: "fishSelect"` field, which `startAction()` in `location.js` branches on generically; choosing a species calls `beginAction("fish", { lootIds, species })`).

### Admin screens (`ui/screens/admin/`)

Eight screens for editing state at runtime: a hub plus editors for stats, skills, inventory, equipment, toolbelt, quests and achievements. **Gated on `game_config.allow_admin`**, resolved by `shared.js`'s `adminEnabled()` — `config.js` itself stays env-free, matching how `logger.js` handles `DEBUG_LEVEL`. **`ALLOW_ADMIN` overrides that flag in both directions**: `"true"` opens the gate, any other non-empty value closes it, and only unset/empty falls through to the config. It was an `||` against the config at first, so the env could only ever *open* the gate — which left `test/integration/admin.test.js`'s closed-gate case leaning on `config.js` shipping `false`, and flipping that flag locally failed a test that had nothing to do with its value. The suite now pins the closed case with `ALLOW_ADMIN=false` and keeps one env-free case that asserts the Menu agrees with whatever `game_config.allow_admin` currently says (the value is in the test's name), so it passes either way and still fails if flag and Menu disagree. The gate is applied twice: `menu.js` hides the `[V] Admin` entry *and* no-ops its handler, and every admin `onEnter` calls `requireAdmin()` to bounce back to the Menu.

- They write state **directly**, bypassing `addItem`'s slot caps, `acceptQuest`'s level/lock gates, `equipItem`, `grantSkillXp` and `completeQuest`'s reward. That's the point — each screen comments on which gate it's stepping around and why.
- **The persistence rule: progression edits persist, live switches don't.** A forced quest objective rides the save; `adminInfinite` and `adminAutoAchievements` are session-only and say so on screen.
- **Godmode** (`state.godmode`, toggled with `G` on the stats editor) covers every way the player spends: damage (`enemyAttack`), mana (`castSpell` **and** `canCastSpell` — the gate has to give way too or the spell is refused before it can be free), money (`data/shops.js`'s `canAfford`/`chargeGold`, thin wrappers over `gameState.js`'s purse helpers — same both-halves reason), items (`removeItem`), and belt water (`spendIngredients`, which bypasses `removeItem` by design). It also guards the `state.hp <= 0` check in `resolveRound` — hp can't be *reduced* to 0, but the stats editor can set it there directly. Seeded from `player_config.godmode` so the config flag still means "start every character in godmode"; the toggle itself is session-only. A `[ GOD ]` badge rides the status bar, since godmode silently changes the rules of every screen.
- **The rule is costs, not moves or voluntary disposals.** `removeItem(state, id, qty, { force })` — `equipItem` (a move to the paperdoll), Drop, and Sell all force; `useItem` and `spendIngredients` don't. Without the carve-out, godmode would make items undroppable and selling would mint money while keeping the goods. `force` covers `adminInfinite` too, which had the same problem.
- Three hooks in core code make the editors possible, each inert when unused: `objectiveStatus()` short-circuits on `record.adminForced[label]` (only 3 of 10 objective types keep a writable counter, so the other 7 can't be forced any other way); `evaluateAchievements()` early-returns when `adminAutoAchievements === false` (it runs every tick and is monotonic — without the pause a re-lock bounces back within a second *and re-pays the reward*); `removeItem()` skips ids in `adminInfinite`.
- Every admin screen draws into `ui.inventoryList`, even the pure field editors — `ui/router.js` has no UP/DOWN tokens, so the list widget is the only thing that gives a movable cursor. Editing is `+`/`-` with `1`/`2`/`3` setting the step to 1/10/100 (`shared.js`'s `stepKeys`/`adjust`). Two traps `shared.js` handles: `render()` must never `select()` (mutation re-renders would snap the cursor to row 0 — same reason `saveSlots.js` documents), and the tab strips use `compactTabLabel` rather than `formatTabStrip` because a 15-entry tab strip ("All" plus the 14 of `ITEM_TYPES`' 16 that any item actually uses) wraps the border label onto a second line and silently eat the list's first row.

### Config (`config.js`)

Centralizes tunables: `app_version`, `file_config` (log/db filenames, log rotation size), `game_config` (`verbose`/`dev`/`debugLevel`/`timeout` — mostly unused so far; `autosaveInterval`/`saveSlots`/`autoSaveFile` — all consumed, by `main.js`'s autosave timer and `state/persistence.js`/`state/autosave.js`; `allow_admin`, consumed by `ui/screens/admin/shared.js`), `server_config` (playercard server host/port, plus `export` gating both export buttons), `player_config` (starting stats — note `finalizeCharacter` in `gameState.js` currently hardcodes starting values from race/starter-pack data rather than reading `player_config`; check both if asked to change starting stats), `combat_config` (all consumed by `data/combat.js`, except `enemySpawnLimit`/`enemyRespawnTime`; `enemySpawnRate` is read by `state/gameLoop.js`'s `shouldAmbush()` as a probability per `logic.actionTic` seconds of gathering — not per tick, and no longer per loot roll), `newgameplus_config` (forward-looking, nothing consumes it yet).
