# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Install: `npm install` (native module `better-sqlite3` will compile on install)
- Run: `npm start` (plain `node main.js`)
- Run with auto-restart on file change: `npm run dev` (`node --watch main.js`)
- No build step — plain ESM, run directly by Node (`"type": "module"`, Node >=18)
- No linter/formatter is configured
- Test suite: `npm test` (unit + integration), `npm run test:unit` (fast, no `tmux` required), `npm run test:integration` (drives the real game via `tmux` — needs `tmux` installed; the directory-form `node --test <dir>` is broken on this project's Node build, so `package.json` globs explicit file lists instead). Integration tests launch `node main.js` inside a detached `tmux` session and drive it with real keystrokes (`test/helpers/tmux.js`, `test/helpers/bootstrapCharacter.js`); several exercise real timed travel and take tens of real seconds to run (see `data/locations.js`'s `time` fields below) — the full suite takes roughly a minute.
- Test isolation gotcha: `db_backbone.js`, `logger.js`, and `state/autosave.js` each open/resolve their file at **import time** from an env var (`DB_PATH`, `LOG_PATH`, `AUTOSAVE_PATH`), and ES module imports fully evaluate before a test file's own top-level code runs. Any unit test needing isolation must set these env vars *before* any static import of a module that transitively imports one of those three, using dynamic `await import()` inside the test body instead of static imports at the top of the file (see `test/unit/persistence.test.js` for the pattern).

Running the game takes over the terminal via neo-blessed's alt-screen buffer. It also starts a plain `node:http` server (`server_backbone.js`, no Express) on `localhost:4000` — configurable via `server_config` in `config.js` — serving `public/index.html`, a read-only "playercard" web page that polls `GET /api/playercard` every 5s for a JSON snapshot of live game state, rendered across five client-side tabs (Playercard, Toolbelt, Backpack, Quests, Achievements — all populated from the same poll, tab-switching is a pure CSS toggle with no extra fetches). The Playercard tab's combat panel and lifetime kill list hide themselves when `payload.combat` is `null` / `payload.kills` is empty, mirroring how the action line collapses to "Idle". The Backpack tab groups the inventory into type sub-tabs, with a second row for subtypes, shown only once there are 3+ categories to navigate; those use `.subtab-btn`/`.subtabs` rather than the top bar's `.tab-btn`, because `showTab()` queries `.tab-btn` **document-wide** and reusing the class would blank every panel on a sub-tab click. The selection lives in module-level state because the page re-renders from scratch every 5s.

Environment-variable overrides (all optional, mainly used for test isolation — see the gotcha above): `DB_PATH` (SQLite save file, `db_backbone.js`), `LOG_PATH` (log file, `logger.js`), `AUTOSAVE_PATH` (autosave JSON file, `state/autosave.js`), `DEBUG_LEVEL` (overrides `game_config.debugLevel`, `logger.js`).

## Architecture

This is a single-process terminal RPG with three cooperating layers: static data catalogs, a state/engine layer, and a hand-rolled screen-router UI layer over neo-blessed.

### Data/"backbone" catalogs

Top-level `*_backbone.js` files plus `data/*.js` are pure-data modules (plain objects/arrays, small pure/behavior helpers, no classes):

- `item_backbone.js` — the largest file (~1130 lines): `ITEMS`, `MYTHIC_ITEMS`, `UNIQUE_ITEMS`, `STARTER_PACKS`, `METALURGY`, `SMITHING_RECIPES`/`CRAFTING_RECIPES`/`COOKING_RECIPES`/`POTION_RECIPES`, `TREASURE_ITEMS`, `STATIONS`, `TOOLBELTS` (belt items — `{ slingAmmo, potions, backpack }` capacity tiers), `SHOP_RARITY_DISPLAY` (rarity → level + color, drives pricing/loot weighting), and `ALL_ITEMS` (merge of every catalog above, via a `withGlobalDefaults()` helper that applies each collection's own `global: {}` tag block).
- `player_backbone.js` — `RACES`, `CLASSES`, `DIFFICULTY_LEVELS`, `STARTER_ITEMS` (granted to every character regardless of race/class/starter pack — e.g. the starter belt).
- `skill_backbone.js` — `SKILLS` (**17** trainable skills, not the 18 the source looks like: `cooking` is declared twice and the second silently overwrites the first, so one intended skill is missing. Left as-is deliberately — `state/persistence.js` derives `SKILL_COLUMNS` from these keys, so adding the lost skill means a schema migration), `skillLevelCost(targetLevel) = round(50 * level^1.4)` (the one XP-cost formula used everywhere leveling happens — both skill levels and the overall player level reuse it), `PROFICIENCY_XP_MULTIPLIER`, `SKILL_BLOCKS` (skill-gated item tiers).
- `quest_backbone.js` — `QUESTS`, playable via `data/quests.js` + the Quest Board/Journal screens (see below). Each quest has `level`/`locked` gating, a `reward` (`gold`, `xp`), and an `objectives` map keyed by a human-readable label. `defeatEnemy` accepts two shapes — `{ type, quantity }` (count kills of an enemy type) and a bare id array (each named enemy required) — both computed live off `state.enemiesDefeated`, so like `acquireItem` they count progress made before the quest was accepted.
- `achievements_backbone.js` — `ACHIEVEMENTS` (7 entries: name/description/reward/`req`), evaluated by `data/achievements.js`. The header comment is the **spec for the whole `req` vocabulary**, and the evaluator implements all 13 types, so a new achievement is pure data. Note `reward.xp` is polymorphic here (`number | { player, skill: {…} }`) where quest reward xp is always a plain number. `slayerrr` needs 5 kills in one encounter, which the larger `GROUP_ENEMIES` packs (6–15 members, in `mountain_peak` and the far regions) now satisfy.
- `magic_backbone.js` — `SPELLS`, consumed by `data/magic.js` + the Spellbook screen.
- `enemy_backbone.js` — `BASIC_ENEMIES`/`GROUP_ENEMIES`/`NAMED_ENEMIES`, plus `ALL_ENEMIES` (flat merge, mirroring `ALL_ITEMS`), `getEnemy()`, `isGroup()` and `expandEnemy()`. Consumed by `data/combat.js`, `data/quests.js`, `state/persistence.js` and `server_backbone.js`.

  **A `GROUP_ENEMIES` entry is not an enemy — it's a header** saying a pack spawned and naming who's in it. It declares only `members`, `name` (shown above the current enemy on the combat screen) and `xp` (a completion bonus, ~30% of the members' combined xp, paid on clearing the pack). It has no hp/dps/type/subtype of its own, is never queued as a combatant, and is **never recorded as a kill** — only members reach `state.enemiesDefeated`. `members` is either a list or a `{ id: count }` map; `expandEnemy()` handles both and returns `[]` (not `[id]`) for a group with no usable members, because queueing a group as a fighter would give it `Math.max(1, NaN)` hp — an enemy that can never die.

  One catalog quirk `test/unit/enemyBackboneConsistency.test.js` pins: 12 mage-subtype enemies carry **no `dps`**, only `spells`, and the engine derives their damage from their best attack spell. The same file also guards the invariant that every spawn-pool entry builds a non-empty encounter with finite hp, and that no pack contains `orc_chieftain` — a `subtype: "boss"` entry in `BASIC_ENEMIES` that would otherwise hand out `boss_down` for a routine fight.
- `data/locations.js` — `LOCATIONS`, each with `exits` (`{ label, to, category, time? }` — `category` is `"shop"`, `"path"`, `"airboat"`, `"cave"`, `"in_cave"` or `"teleport"` — it selects the traveling screen's animation, and `ui/screens/traveling.js` treats anything unrecognised as a road, so a new category renders rather than crashing; an exit with a `time` value, in seconds, becomes a real timed trip via `data/travel.js`, one without it stays instant), an optional `mine` field naming a `MINE_LOCK` tier (read by `getMineType()`, consumed by `data/mining.js` — a location with the `mine` hub feature but no `mine` field lists nothing), and a `flavorText` that is **either a plain string or an array** whose entries may be `(state, location) => string | null` functions (see `data/flavor.js`). `resolveFlavorText(location, state)` at the bottom of the file turns either shape into the lines to render: a `null` result **drops its line**, and consecutive blanks **collapse**, so a conditional line that stays quiet doesn't leave a double gap. Functions are called unguarded, like `verbFlavor`/`requires` — and since the location screen now re-renders every tick, a throwing one fails immediately rather than lurking. Most locations are still one string; only a handful are converted, `interactiveActions`, `hubFeatures`, optional `openHours`, and — on locations with `safe: false` — an `enemies` spawn pool plus an optional `boss` id list, both read by `data/combat.js`. The two black-market interiors are `safe: false` but deliberately have no pool (and no actions at all), which `test/unit/enemyBackboneConsistency.test.js` pins as a known exception. Not every `exit.to` in this file resolves to a defined location yet (`vetron_station`/`kooz_station` both point at undefined ids) — `ui/screens/travel.js`'s digit handler guards against this defensively rather than crashing on arrival.
- `data/actions.js` — `ACTIONS`, in three flavours distinguished by flags that `ui/screens/location.js`'s `startAction()` branches on: timed gathering actions like `gather_scraps`/`fish`/`chop` (the default), `instant: true` actions like `rest` that mutate state immediately, and `combat: true` actions (`fight`, plus `challenge_boss` which is additionally gated on `SKILL_BLOCKS.fighting.boss.all.level`) that hand off to `data/combat.js`. Also `beginAction(state, actionId, extra)` (shared constructor snapshotting the acting skill's level/xp for later "gained this session" deltas), and `rollLootByType()`, a rarity-weighted loot roller over `ALL_ITEMS`.
- `data/achievements.js` — the achievements evaluator, mirroring `data/quests.js`: `requirementStatus()` (the analogue of `objectiveStatus()`), `isUnlocked`/`isEarned`, `achievementRows()` (feeds both the screen and the web payload), `grantAchievementReward()` and `evaluateAchievements(state, ctx)`. There is **no accept/claim step** — achievements unlock and pay out the instant their requirement holds, and multiple `req` keys on one achievement are ANDed. Called every tick from `state/gameLoop.js` for the live-derivable requirements, plus once with a `{ combatEnd }` context from `data/combat.js` the moment a fight is *won* (a flee or a death doesn't qualify, and hooking at `endCombat()` instead would read post-revival hp because `resolveDefeat()` restores it first). Two deliberate divergences from the quest equivalents, both commented in place: `reachLocation` means "have reached" (reads `state.locationsVisited`) rather than quests' "standing there right now", and the `combatEnd` `*Max` fields are **upper bounds**, not floors.
- `data/combat.js` — the turn-based combat engine. `spawnEncounter`/`buildEncounter` (an encounter is a **queue** of enemies fought one at a time; a group expands into its members, and `combat.sourceId` keeps the group id so the screen can name the pack and victory can pay its xp bonus), `beginCombat`/`endCombat`, `resolveRound(state, action, rng)` (one keypress = one full exchange: player action, then the enemy's), `resolveDefeat`, `attemptFlee`, `usePotion`, plus the exported stat helpers (`playerAttackPower`/`playerDefensePower`/`damageReduction`/`critChance`/`dodgeChance`/`blockChance`/`enemyStrike`). **Every rolling function takes an `rng` last parameter defaulting to `Math.random`** so tests inject determinism rather than stubbing globals — `rollLootByType` in `data/actions.js` gained the same parameter for this. Armor mitigation is a percentage with diminishing returns (`total/(total+K)`, capped at 80%), *not* flat subtraction — equipped `defense` sums past 300 and would otherwise zero out every hit. Note this module deliberately never imports `state/persistence.js`: permadeath only sets a flag, and `ui/screens/defeat.js` does the deleting (see the import-time DB gotcha above).
- `data/travel.js` — `beginTravel(state, exit)`/`tickTravel(state)` for timed travel: sets up `state.currentTravel`, ticks it once per game-loop second, and on completion grants the exit's `time` value as `speed` skill XP, moves `state.currentLocationId`, and clears itself.
- `data/shops.js` — `getBuyPrice`/`getSellPrice` derived from item rarity, `getBarterXp`, `isPurchasable` gated by barter skill level.
- `data/stations.js` — derives `STATION_RECIPES` by reading each recipe collection's own `global: {station, skill}` block in `item_backbone.js`. **This is the codebase's one explicit "add data, not code" extensibility point**: a new recipe collection needs no changes here. `playerhome` is the one location whose stations come from `state.ownedStations` instead of static `hubFeatures`.
- `data/hubFeatures.js` — `HUB_FEATURES`, non-travel location amenities, each with a globally-unique `hotkey` and either a `to` (location transition), a `screen` (e.g. `quest_board` → `"questBoard"`), a shop link, or a stub `message`. Note `"q"`/`"Q"` can never be used here — `main.js` binds a global hard-quit on those keys that fires independently of the screen-level keymap.
- `data/items.js` — **the one place a consumable is consumed.** `consumeEffectOf(itemId)` (the classifier, symmetric sibling of `item_backbone.js`'s `equipSlotOf()` — id → `{kind, amount?, stat?, targets?}` or `null`) and `useItem(state, itemId, ctx)`, where `ctx` is `{target, combat}` supplied only by combat. Both the backpack's `U` and `data/combat.js`'s `usePotion()` (now a thin wrapper) route through `useItem`, so `item_backbone.js`'s `CONSUME` economy — skill xp plus a byproduct (`empty_bottle` for potions) — applies wherever a consumable is used; same "one hook where it actually happens" reasoning that keeps `recordSpellCast` inside `castSpell()`. Two things to know: food is gated on `health_boost` being present, not on `type === "food"`, because the ten `subtype: "ingredient"` foods (flour, yeast, dough) are crafting inputs; and `useItem` returns `{used, message}` rather than the `string | null` of `learnSpell`/`castSpell`, because every refusal here has a distinct reason (full health vs. not poisoned vs. not usable) and callers shouldn't have to guess. `cure` items always refuse — the player carries no status effects for one to remove. `revive` refuses off the backpack too, because it isn't used on purpose: `attemptRevive(state)` is the **pre-death hook**, called from `resolveRound()` the instant `state.hp <= 0` and *before* `resolveDefeat()` (which is what permadeath hangs off, so intercepting earlier is what saves the run). It spends the weakest revive in the backpack — `revive` is a *subtype*, so a revive potion qualifies as readily as the aid item — and returns `null` when there's none, leaving the caller to die as it would have. A bare `revive: true` restores fully; a numeric `revive` is read as a fraction of `hpMax`.
- `data/toolbelt.js` — belt-derived capacity: `hasBeltEquipped`, `slingshotAmmoCap`, `waterBottleCap`, `quiverCap` (can be `Infinity` once any belt is equipped — see the JSON-encoding note in `server_backbone.js` below), `backpackSlotCap`, `potionSlotCap`, `backpackSlotsUsed`, `potionSlotsUsed`.
- `data/flavor.js` — ready-made `flavorText` entries: `timeLine`/`indoorTimeLine` (dawn/morning/afternoon/dusk/night), `weatherLine`, `openLine` (reads the location's `openHours`), `firstVisitLine`, `dangerLine`, `healthLine`, `packLine`. Each is `(state, location) => string | null`, and the `null` is load-bearing — it's how a line appears only when it has something to say. **Weather is derived from the clock, not stored**: hashing the day and a ~4-hour block gives something that holds steady, drifts on its own, and survives a reload with no state, no transitions and no save migration. **This file must not import `state/gameState.js`** — gameState imports `data/locations.js`, which imports this, so that would close the loop; the day-wrapping clock maths it needs lives in the leaf `state/clock.js` instead (which also de-duplicated the two copies gameState was carrying).
- `data/mining.js` — `mineableOres(locationId?)`, `canMineOre(state, oreId)`, `rollMineBonuses(state, rng?)`. Two independent gates: **which ores exist here** (the location's `mine` tier, via `item_backbone.js`'s `MINE_LOCK`/`isMineableAtTier`) and **whether you can mine one** (mining skill level plus equipped pickaxe tier — so every level in `SKILL_BLOCKS.mining.ores` needs a pickaxe in `.tools` that can reach it, or the ore is listed and permanently unmineable). Tiers are **cumulative** — a `mid_tier` mine yields everything `basic` does plus its own — and an ore listed in *no* tier is unlisted rather than forbidden, so it shows everywhere (otherwise adding an ore item would silently make it unmineable until someone filed it under a tier). `MINE_LOCK` keys `metals` by item **subtype** but `gems`/`fuel` by item **id**, because every gemstone shares the subtype `"gemstone"` and every fuel `"fuel"`; `isMineableAtTier` matches either. Omitting `locationId` applies no gate at all.
  **Coal and gemstones are not selectable ores** — `mineableOres` filters both subtypes out, and `rollMineBonuses` drops them as separate per-roll extras on top of the chosen ore (called from `state/gameLoop.js` when the action is `mine`). They have to be rolled here rather than folded into `lootSubtype`, for two reasons: `rollLootByType` matches on subtype, so the literal `"gemstone"` would let a tier-1 mine yield a legendary diamond — hence its `allowIds` parameter, appended fifth so `data/combat.js`'s positional `undefined, undefined, rng` call still works; and sharing one pool meant fuel's four `common` items outweighed the single ore 4:1. `rng` is injectable because the game loop's roll block has no unit coverage.
- `data/quests.js` — `visibleQuests`/`startedQuests` (level+lock gated listing / the player's own accepted quests), `objectiveStatus` (per-objective `{current, target, complete}` — most objective types are computed live off existing state; `sellItem`/`craftItem` are the two exceptions, tracked via small event counters since they can't be reconstructed from current state alone), `acceptQuest`/`completeQuest`/`claimCompletedQuests`, and the event hooks `recordItemSold`/`recordItemCrafted`/`recordSpellCast`/`recordEnemyDefeated` (from `shopSell.js`, `stationCraft.js`, `data/magic.js`'s `castSpell()` and `data/combat.js` respectively). Each hook also bumps the matching `state.lifetime` ledger, because its per-quest counter only fires for quests that are currently `in_progress` — with no matching quest accepted the event would otherwise be recorded nowhere, which is no basis for an achievement. Note `recordSpellCast` lives inside `castSpell()` rather than at its call sites: it used to be called only from the spellbook screen, so every spell cast in combat went unrecorded.

### State/engine layer (`state/`)

- `gameState.js` — `createInitialState()` defines the full mutable state shape (hp/mp/gold/level/xp, `currentLocationId`, `clock.totalMinutes`, `inventory`/`skills` maps, `equipment`, `toolbelt`, `currentAction`, `currentTravel`, `currentCombat`, `enemiesDefeated` (the lifetime `{enemyId: count}` tally behind `defeatEnemy` objectives), `saveSlotId` (which slot the session is bound to, so permadeath knows what to delete — set by `ui/screens/saveSlots.js` on both save and load), `achievements` (`{id: {unlockedAt}}`, key presence *is* the unlocked flag), `locationsVisited` Set, `lifetime` (`{sold, crafted, cast, used}`, id-keyed so achievements' by-type/by-subtype shapes derive through `ALL_ITEMS`/`SPELLS`; `used` is written by `data/items.js` but no objective/`req` type reads it yet — adding a ledger key also means adding it to `state/persistence.js`'s hardcoded load-side list, since the save side iterates generically and would otherwise drop the rows silently on load), `toasts`, `quests`, `currentScreen`/`returnScreen`/`menuOrigin`, `characterDraft`, `ownedStations` Set, and the three session-only switches `adminInfinite`/`adminAutoAchievements`/`godmode`, the last seeded from `player_config.godmode`). `equipment` carries all 13 slots including `shield`/`cloak`/`ring`/`necklace` — those four used to be missing or dropped on save even though 23 catalog items equip into them. Also `moveTo(state, locationId)` — **the single choke point for changing location**, so `locationsVisited` can't drift; everything that moves the player (travel completing, an instant exit, a hub feature, a teleport spell, the defeat respawn) goes through it rather than assigning `currentLocationId` directly. And `pushToast`/`activeToast`, whose expiry rides on `clock.totalMinutes` (already advanced once per tick) rather than a second timer. Also holds pure(ish) mutators: `addItem`/`removeItem` (capacity-aware, belt-gated via `data/toolbelt.js`; `removeItem` takes a fourth `{ force }` option — see the godmode note in the Admin section for which callers pass it and why), `equipItem`, `grantSkillXp` (applies proficiency + difficulty multipliers, loops level-ups against `skillLevelCost`, and — per level gained — grants a fraction of `skillLevelCost(newLevel)` as **player** xp via `grantPlayerXp`), `grantPlayerXp` (the overall player level, reusing the same `skillLevelCost` curve), `finalizeCharacter(state, draft)` (converts the character-creation wizard draft into a real character), and `formatClock`/`isSafeZone`/`isLocationOpen`.
- `gameLoop.js` — `startGameLoop(state, onTick)`, a 1-second `setInterval` tick: advances the clock; while an action is running, increments `elapsedSeconds` and every 3rd tick rolls loot + grants skill XP (`SKILL_XP_PER_GRANT = 5`); while `state.currentTravel` is set, calls `tickTravel(state)` (`data/travel.js`). Also exports `shouldAmbush(state, rng)` and, on the same 3rd-tick cadence, can interrupt a gather in an unsafe zone with a real encounter. Calls `onTick(state)` after every mutation so the caller (`main.js`) decides how to re-render — the screens needing a per-tick re-render are `"action"`, `"traveling"` and `"location"` (the last because `data/flavor.js`'s lines are computed per render, so a line about dusk would otherwise sit frozen until the next keypress); **combat is turn-based and deliberately needs none**. Because the loop has no `ui` handle, an ambush only sets `state.currentCombat`, and `main.js`'s `onTick` does the actual `switchScreen` to `"combat"`.
- `persistence.js` — **multi-slot** save/load. Two things bite when adding fields: `db_backbone.js`'s `CREATE TABLE IF NOT EXISTS` never adds a column to an existing database, so a new column needs an explicit `PRAGMA table_info` + `ALTER TABLE` migration beside the ones for `saved_at`/`quest_objectives_json`/`health_max`/`mana_max` (covered by `test/unit/dbMigration.test.js`, which seeds an old-shape DB — a fresh-schema test passes off `CREATE TABLE` alone and proves nothing). And `quest_objectives_json` now holds a `{progress, adminForced}` envelope; a parsed object with no `progress` key is read as a legacy bare progress map, so "progress" must never be a real objective label. Save/load via `better-sqlite3` prepared statements in an explicit transaction: `saveGame(state, slotId)`/`loadGame(slotId)`/`deleteSave(slotId)`/`listSaveSlots()` (slot ids `1..game_config.saveSlots`). Child tables (inventory/proficiencies/stations/spells/quests/enemies_defeated/achievements/locations_visited/lifetime_counters) are deleted and rewritten wholesale each save — no diffing. The long-unused `achievements` table needed no `ALTER TABLE` migration: unlocking is binary and progress is always recomputed from live state, so its existing columns suffice. `state.currentAction`/`state.currentTravel`/`state.currentCombat` are intentionally never persisted — loading always resumes idle and out of combat.
- `autosave.js` — a single JSON snapshot (`AUTOSAVE_PATH`, default `data/autosave.json`), separate from the numbered SQLite slots: `writeAutosave`/`readAutosave`/`autosaveSummary`. Written on a timer in `main.js` (`game_config.autosaveInterval` seconds), and offered as an extra loadable entry (not a numbered slot) in the save-slot picker.

### UI layer (`ui/`) — hand-rolled screen router over neo-blessed

Each screen in `ui/screens/*.js` (30 files) is a plain object implementing the same contract, registered via `registerScreen(name, screen)` in `main.js`:

```js
{
  keymap: { <UPPERCASE_KEY_OR_"ESCAPE">: (state, ui) => { ... } },
  onEnter?(state, ui),
  onExit?(state, ui),
  render(state, ui),
}
```

- `ui/router.js` — `switchScreen(state, ui, name)` calls `onExit` on the outgoing screen, sets `state.currentScreen`, then calls `onEnter` + `render` on the incoming one. `handleKey` is the single `screen.on("keypress", ...)` handler wired once in `main.js`; it uppercases the pressed key (or maps Escape/Left/Right to named tokens), looks it up in the current screen's `keymap`, runs the handler, then re-renders.
- `ui/layout.js` — `buildLayout()` builds the fixed blessed widget tree: a 3-column header (`headerLeft`/`headerCenter`/`headerRight` — title+name+level+location+gold, current action name or `[idle]`, and a right-hugging clock), a status bar, a content pane, and a command box, plus hidden text inputs for name entry. Forces `terminal: "xterm-256color"` on the blessed screen — neo-blessed's terminfo lookup otherwise under-detects color depth for several common `TERM` values (confirmed for `tmux-256color`), silently degrading every hex color tag to a crude 8-color approximation. `renderChrome()` renders the shared header/status bars on every screen, with color throughout: a bold blue title, the player's name bold white with `Lv.N` beside it (via `headerIdentity()`, which **omits the whole segment when `state.name` is null** — the header draws on the title screen and every creation-wizard step too, and truncates long names so they can't push `gp:` off the 50%-wide column; `app_version` moved to the title screen when this took its place, and `ui/screens/title.js` is now its only consumer), the location name bracketed in green/red by safe-zone status, gold/location name in a yellow-orange, HP/MP bolded and percentage-banded (green→white→blue→orange→red for HP, light-blue→blue→dark-blue→red for MP), and — while an action is running — a percentage-banded XP progress bar (`formatXpBar`/`actionProgressText`, white→blue→yellow→green→gold, bold from yellow up). An achievement unlock toast (gold, bold) takes that same tail slot while live: unlocks can happen on any screen, including ones that never render `state.lastMessage`, so they ride the one bar every screen draws.
### Settings (`state/settings.js` + `state/displaySettings.js` + `ui/screens/settings.js`)

Menu → `[T]`. Backed by `game_settings`, a **single row at `id = 1`** (settings belong to the install, not a character), bootstrapped on first read rather than by a migration. Two columns are live — `colorize` and `action_key` — plus the `first_run`/`last_run`/`last_autosave` stamps; the rest of the table (`terminal_*`, `dev_*`, `account_id`) is deliberately untouched.

- **Two layers, and the split is load-bearing.** `state/displaySettings.js` imports **nothing** and holds the live copy; `state/settings.js` owns the DB row and pushes into it. `ui/format.js` reads only the former, because it's imported by 37 screens and by `renderChrome` — pointing it at the DB module would drag `db_backbone.js`'s import-time SQLite open into `format.test.js`/`layout.test.js`/`spellbookScreen.test.js`, all of which import it statically. Reads also can't hit the DB per call: `colorTag` fires dozens of times per render and `renderChrome` runs every second.
- **`action_key` styles**, via `formatCommandCell`: `B` boxed key (`[T]ravel`, the default and the pre-settings behaviour), `P` prefix (`[T] Travel`), `R` bolded (`{bold}T{/bold}ravel`), `S` boxed action (`T: [Travel]`). Only `R` needs a fallback — with the hotkey nowhere in the label there's no letter to embolden, so it uses the prefix form. That isn't an edge case: `<>`, `+-`, `123`, `1-7` and every digit-keyed row on the location and travel screens hit it. **`R` emits markup inside a padded cell**, so `formatCommandRow` pads on the tag-stripped length; padding on raw length throws the legend out by 13 characters per cell.
- **`colorize: 0` drops colour but keeps `{bold}`**, and leaves `inventoryList`'s `inverse: true` alone — both are video attributes (SGR 1 / SGR 7) that render on a monochrome terminal, and inverse is the *only* selection indicator on 12+ list screens. The gate lives in `colorTag`, so nothing may emit a raw `{...-fg}` tag; `renderChrome` had five that had to be routed through it.
- **The `B` default is deliberate**: 13 integration tests `waitFor` strings like `"[S]ave"`, and they time out rather than fail fast if the format shifts under them.
- **`game_settings` shipped unusable.** It declared `FOREIGN KEY(account_id) REFERENCES player(id)` with `account_id TEXT NOT NULL DEFAULT ''` against an INTEGER `player.id`, and better-sqlite3 enables `PRAGMA foreign_keys` by default — so every insert died with "FOREIGN KEY constraint failed". That's why the table had zero rows. `db_backbone.js` now rebuilds the table without it (SQLite can't drop a constraint in place) and backfills `action_key`; both migrations only ever fire on a pre-existing database, so `test/unit/dbMigration.test.js` seeds the old shape to reach them.

- `ui/format.js` — `formatCommandRow()` turns `{label, hotkey}` lists into the aligned `[T]ravel | [L]ook for food | ...` legend (see `apocylta-gui.md` for the intended visual layout of each screen). Also `colorTag(text, color, bold)`, the one place blessed's `{green-fg}`/`{/green-fg}` markup is built — used by `renderChrome`'s banded stats and by `ui/screens/spellbook.js`. Note tags inflate string length, so any `padEnd` alignment has to be computed on the plain text, and `inventoryList`'s `selected: { inverse: true }` style turns a colored row's foreground into its background while highlighted.
- Screens: `title` (New Game / Continue, the latter opening the shared save-slot picker), `charName`/`charDifficulty`/`charStarterPack`/`charRace`/`charClass`/`charSkills` (the character-creation wizard, staged into `state.characterDraft` and finalized via `finalizeCharacter`), `location` (main hub — builds numbered actions + hub-feature hotkeys dynamically from the current location), `travel` (digit-hotkey destination picker; instant for exits with no `time`, otherwise hands off to `traveling`), `traveling` (countdown + a category-specific ASCII animation — a walker along a road for `"path"`, a glider over "sky" for `"airboat"`, a cart in a tunnel for `"cave"`/`"in_cave"`, a shimmer for `"teleport"`; `buildTravelTrack` clamps the marker's position against **its own length** rather than a fixed one, since the markers differ in width and a hardcoded clamp let the longer ones render a track wider than `TRACK_WIDTH` — ticks in the background regardless of which screen is active, so its `render()` has to defensively re-route to `location` if `state.currentTravel` completed while the player was elsewhere), `action` (in-progress gathering), `combat` (the turn-based fight — one keypress resolves one round, so unlike `action`/`traveling` it needs no per-tick render; `render()` still defensively re-routes to `location` if the encounter ended while the player was on another screen), `combatSelect` (one shared Cast/Potion picker parameterised by `state.combatSelectContext.mode`, following `saveSlots.js`'s shared-picker precedent), `defeat` (the death summary — **owns the permadeath side effects**: deleting the save slot and the autosave file), `backpack` (tabbed by item type), `spellbook` (reached from `backpack`'s `C`; tabbed Learned/Unlearned, the latter sub-grouped [Learnable]/[Unlearnable] then by spell type, rows colored green/red — the only screen that colors its own content rather than leaving color to `renderChrome`. Deliberately does **not** filter by `isSpellUnlocked`: a spell above your magic level is listed with a `req: magic lv N` reason instead of hidden, and learn costs render as owned/required counts via `data/stations.js`'s `ingredientCount`), `toolbelt` (equipped tool/slingshot/belt + belt-derived capacities; also the entry point to `toolSwap`/`slingshotSwap`/`journal`), `journal` (accepted quests, objective checklists, batch-claim rewards), `achievements` (the full catalog grouped unlocked/locked with live per-requirement progress; reached from the Menu's `A`, and one of the few screens using `inventoryList` purely for its keyboard scrolling — nothing in it is selectable), `questBoard` (level/lock-gated quest listing, Accept), `menu`, `saveSlots` (shared save/load picker used by both the title screen and the menu, with a two-press confirm pattern for overwrite/delete), `shopBuy`/`shopSell`/`shopHousing`, `stationSelect`/`stationCraft`, `mineSelect`.

`main.js` is the entry point: registers all screens, creates initial state, `await`s `startPlayercardServer(state)` (awaited so its startup log prints before blessed takes over stdout), builds the layout, wires `q`/`Q`/`C-c` to hard-quit and the global keypress handler, starts the game loop (re-rendering chrome + the `action`/`traveling` screens every tick, per the per-tick-render note above), starts the autosave timer, then switches to the `title` screen.

### Admin screens (`ui/screens/admin/`)

Eight screens for editing state at runtime: a hub plus editors for stats, skills, inventory, equipment, toolbelt, quests and achievements. **Gated on `game_config.allow_admin`** (or `ALLOW_ADMIN=true`, resolved by `shared.js`'s `adminEnabled()` — `config.js` itself stays env-free, matching how `logger.js` handles `DEBUG_LEVEL`). The gate is applied twice: `menu.js` hides the `[V] Admin` entry *and* no-ops its handler, and every admin `onEnter` calls `requireAdmin()` to bounce back to the Menu.

- They write state **directly**, bypassing `addItem`'s slot caps, `acceptQuest`'s level/lock gates, `equipItem`, `grantSkillXp` and `completeQuest`'s reward. That's the point — each screen comments on which gate it's stepping around and why.
- **The persistence rule: progression edits persist, live switches don't.** A forced quest objective rides the save; `adminInfinite` and `adminAutoAchievements` are session-only and say so on screen.
- **Godmode** (`state.godmode`, toggled with `G` on the stats editor) covers every way the player spends: damage (`enemyAttack`), mana (`castSpell` **and** `canCastSpell` — the gate has to give way too or the spell is refused before it can be free), gold (`data/shops.js`'s `canAfford`/`chargeGold`, same both-halves reason), items (`removeItem`), and belt water (`spendIngredients`, which bypasses `removeItem` by design). It also guards the `state.hp <= 0` check in `resolveRound` — hp can't be *reduced* to 0, but the stats editor can set it there directly. Seeded from `player_config.godmode` so the config flag still means "start every character in godmode"; the toggle itself is session-only. A `[ GOD ]` badge rides the status bar, since godmode silently changes the rules of every screen.
- **The rule is costs, not moves or voluntary disposals.** `removeItem(state, id, qty, { force })` — `equipItem` (a move to the paperdoll), Drop, and Sell all force; `useItem` and `spendIngredients` don't. Without the carve-out, godmode would make items undroppable and selling would mint gold while keeping the goods. `force` covers `adminInfinite` too, which had the same problem.
- Three hooks in core code make the editors possible, each inert when unused: `objectiveStatus()` short-circuits on `record.adminForced[label]` (only 3 of 10 objective types keep a writable counter, so the other 7 can't be forced any other way); `evaluateAchievements()` early-returns when `adminAutoAchievements === false` (it runs every tick and is monotonic — without the pause a re-lock bounces back within a second *and re-pays the reward*); `removeItem()` skips ids in `adminInfinite`.
- Every admin screen draws into `ui.inventoryList`, even the pure field editors — `ui/router.js` has no UP/DOWN tokens, so the list widget is the only thing that gives a movable cursor. Editing is `+`/`-` with `1`/`2`/`3` setting the step to 1/10/100 (`shared.js`'s `stepKeys`/`adjust`). Two traps `shared.js` handles: `render()` must never `select()` (mutation re-renders would snap the cursor to row 0 — same reason `saveSlots.js` documents), and the tab strips use `compactTabLabel` rather than `formatTabStrip` because 15 item types wrap the border label onto a second line and silently eat the list's first row.

### Config (`config.js`)

Centralizes tunables: `app_version`, `file_config` (log/db filenames, log rotation size), `game_config` (`verbose`/`dev`/`debugLevel`/`timeout` — mostly unused so far; `autosaveInterval`/`saveSlots`/`autoSaveFile` — all consumed, by `main.js`'s autosave timer and `state/persistence.js`/`state/autosave.js`), `server_config` (playercard server host/port), `player_config` (starting stats — note `finalizeCharacter` in `gameState.js` currently hardcodes starting values from race/starter-pack data rather than reading `player_config`; check both if asked to change starting stats), `combat_config` (all consumed by `data/combat.js`, except `enemySpawnLimit`/`enemyRespawnTime`; `enemySpawnRate` is read by `state/gameLoop.js`'s `shouldAmbush()` as a per-loot-roll — not per-tick — probability), `newgameplus_config` (forward-looking, nothing consumes it yet).
